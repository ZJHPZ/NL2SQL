# 分组后筛选：HAVING 与行级过滤别混

## 何时用

问句在"按某维度分组"之后还要对结果加条件，例如：
"平均订单金额超过 200 的渠道有哪些""订单数超过 100 的品类""每个渠道销售额前 3 的商品"。

## 步骤

1. **先判断条件作用在"行"还是"组"**：
   - 行级：单笔订单金额 > 200、状态 = 已支付 → 过滤**明细行**，用 WHERE。
   - 组级：该组平均/总额/计数满足条件 → 过滤**聚合后的分组**，用 HAVING
     （或先聚合到子查询、外层再筛）。
2. **组级条件绝不能写进 WHERE**。WHERE 在聚合之前生效：
   - `WHERE 平均金额 > 200` 要么语法不成立，要么被解释成行级条件，
     结果从"平均高的组"悄悄变成"只统计大额订单"——数字看起来合理但是错的。
3. **组内前 N / 排名**用窗口函数（按分区排序后取行号），
   不要用整表 LIMIT 截取（LIMIT 截的是结果行，不是每组前 N）。
4. 回答里说明"这些是满足条件的分组"，并给出条件本身
   （阈值、指标口径、是否含空组），让别人能复现。

## 若能力不足

- 语义层不支持组级阈值或组内排名：可以手写 SQL，但必须**说明为什么**、
  并披露阈值与口径。
- 拿不到底层明细或聚合能力：如实说"当前能力下无法按这个条件筛分组"，
  给出能给的部分（例如不筛选的分组结果 + 说明），不要假装已按条件筛过。
- 不要用"少给几行"冒充"已按条件筛选"。

## 反面例子

- "平均订单金额超过 200 的渠道" → `WHERE amount > 200`：
  这是**行级**过滤，留下的是大额订单，不是平均高的渠道。
- "每个渠道销售额前 3 的商品" → `ORDER BY 销售额 DESC LIMIT 3`：
  只截了全表前 3 行，不是每个渠道各 3 个。
- 把组级条件写进 `WHERE` 后没有报错，就默认它对了——最危险的一种。
