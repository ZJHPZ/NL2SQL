# 01 仓库结构与依赖方向

> P0 落地蓝图。原则：**核心与壳物理隔离**，依赖方向单向，可用脚本强制检查。

---

## 1. 顶层布局

```
talk-to-sql/
├── pyproject.toml            # 工作区根，声明多个包
├── README.md
├── .gitignore
│
├── nl2sql/                   # ★ 核心引擎（可独立 pip 安装，无 Web 依赖）
├── apps/                     # 三个壳：只做适配，不含业务逻辑
│   ├── web/                  #   壳①：本地 Web 前后端（首发）
│   ├── sdk/                  #   壳②：对外 Python SDK
│   └── internal/             #   壳③：内部工具外壳
│
├── golden_set/               # 评测集（已存在，视为独立工程资产）
├── scripts/                  # 开发脚本（层依赖检查、数据准备）
├── docs/                     # 本目录
└── data/                     # 运行时数据（gitignore）
    ├── app.db                #   元数据 + 知识库（SQLite，默认）
    └── cache/                #   结果缓存
```

**为什么核心是一个独立顶层包而不是 `apps/core/`**：
壳要能被删除而不影响核心，核心要能被第三方直接 `pip install`。
一旦核心藏在 `apps/` 里，抽 SDK 时就会被迫搬代码。

## 2. 三层依赖方向（单向，禁止反向）

```
        ┌──────────────────────────────────────────┐
        │  Shells   apps/web · apps/sdk · apps/内部  │
        │  职责：HTTP / UI / 进程入口 / 配置装配      │
        └───────────────────┬──────────────────────┘
                            │ 只允许向下
        ┌───────────────────▼──────────────────────┐
        │  Engine   nl2sql（对外唯一门面）            │
        │  NL2SQL 类 + 各模块                       │
        └───────────────────┬──────────────────────┘
                            │
        ┌───────────────────▼──────────────────────┐
        │  Contracts  nl2sql/contracts（只依赖标准库）│
        └──────────────────────────────────────────┘
```

| 方向 | 允许 | 说明 |
|---|---|---|
| Shell → Engine | ✅ | 壳调用核心 |
| Engine → Contracts | ✅ | 核心实现契约 |
| Shell → Contracts | ✅ | 壳可传参/读类型 |
| **Engine → Shell** | ❌ | 核心不得 import 任何 `apps/*` |
| **Contracts → Anything** | ❌ | 契约层只依赖标准库 |
| **Shell ↔ Shell** | ❌ | 三个壳互不引用 |

### 硬约束（会被 `scripts/check_layers.py` 拦截）

1. `nl2sql/` 内**不得出现** `fastapi` / `flask` / `uvicorn` / `starlette` / `jinja2`
2. `nl2sql/` 内**不得** `import apps`
3. `nl2sql/contracts/` 内**不得** import `nl2sql` 其他子模块
4. `nl2sql/` 内**不得有模块级可变全局状态**（连接、缓存、单例）；一律通过显式注入

> 第 4 条没有静态检查，靠 code review + 一条规矩：**模块级只允许常量与类定义**。

## 3. 核心模块清单

| 模块 | 职责一句话 | 依赖 |
|---|---|---|
| `contracts/` | 全部接口与数据模型定义 | 仅标准库 |
| `config.py` | 配置模型与加载（pydantic） | contracts |
| `registry.py` | 组件注册与查找（适配器/检索器/DAG 节点） | contracts |
| `errors.py` | 统一异常层次 | — |
| `storage/` | 元数据 / 知识库 / 历史 / 缓存的持久化 | contracts |
| `sources/` | 数据源适配器（capability + 连接 + 元数据 + 执行） | contracts, storage |
| `dialect/` | sqlglot 方言编译与校验 | contracts |
| `catalog/` | 元数据快照与缓存 | contracts, storage |
| `semantics/` | dbt metrics.yml → 语义模型 → 逻辑计划（`dbt_loader.py` + `contracts/semantic.py`） | contracts, storage |
| `knowledge/` | 知识条目、版本、检索、自动生成 | contracts, storage |
| `guard/` | 执行前安全守门（只读/LIMIT/超时） | contracts |
| `cache/` | 结果缓存（指纹 → 结果） | contracts, storage |
| `agent/` | LangGraph 编排：问题 → 结果 | 以上全部 |
| `api.py` | 对外门面 `NL2SQL` 类 | agent 等 |

## 4. 壳的布局（三个壳对称）

```
apps/web/
├── backend/          # FastAPI 应用：路由、SSE、请求模型
│   ├── main.py
│   ├── routers/
│   └── schemas.py
├── frontend/         # 结果表 / SQL 展示与二次编辑 / 知识库管理
└── README.md         # 启动方式

apps/sdk/             # 只做导出与便利封装，不含逻辑
└── __init__.py       # from nl2sql import NL2SQL 的再导出 + 便捷构造

apps/internal/        # 内部工具外壳：Web + 定制
```

**壳的三条纪律**：

| 纪律 | 原因 |
|---|---|
| 不写业务逻辑，只做参数装配与格式转换 | 换壳不该改行为 |
| 通过显式配置构造核心，不读全局 | 核心无全局状态 |
| 依赖核心的公开路径，不 import 内部私有模块 | 保护重构自由 |

## 5. 一次查询的调用链

```
[Shell]  POST /query
   │
   ├─ 构造 NL2SQL(config)                    ← 壳负责配置装配
   │
   └─ nl2sql.ask(question, source_id="local_mysql")
        │
        ├─ agent.graph      意图识别 + 选语义 + 选召回
        ├─ knowledge.hybrid 检索知识条目（仅 active）
        ├─ semantics.compile 指标 + 维度 + 过滤 → LogicalPlan
        ├─ cache.lookup     用 plan.fingerprint 查结果缓存 ──┐ 命中则直接返回
        ├─ dialect.compile  LogicalPlan → 方言 SQL           │
        ├─ guard.check      只读白名单 / 强制 LIMIT / 超时    │
        ├─ sources.execute  适配器执行                       │
        ├─ cache.store      回写结果（按 data_source 隔离）◀─┘
        └─ 返回 QueryResult(sql, columns, rows, meta)
```

**关键点**：缓存查在**语义层之后**。因为缓存键是逻辑计划指纹，不是问题文本——
问题换个说法，只要计划相同就能命中；这正是设计意图（纯文本相似度缓存已明确去掉）。

## 6. 落地顺序（每步可独立验收）

| 步 | 内容 | 验收方式 |
|---|---|---|
| S1 | `contracts/` + `config.py` + 层检查脚本 | `check_layers.py` 通过 |
| S2 | `sources/` SQLite 适配器 + `catalog/` | 能列出表与注释 |
| S3 | `dialect/` + `guard/` + `cache/` | 黄金集 30 题用**手写计划**跑通 |
| S4 | `semantics/`（dbt metrics.yml）+ `agent/` 最小图 | `evaluate.py` 出第一份准确率 |
| S5 | `apps/web` 后端 + 前端结果表 | 浏览器可问答 |
| S6 | `knowledge/`（条目+版本+测试检索+自动生成） | 知识入库可提升准确率 |
| S7 | `apps/sdk` 抽包 | 三行代码可用 |
| S8 | MySQL 适配器 + 缓存隔离验证 | 双数据源不串缓存 |
| S9 | 多方言（sqlglot） | 黄金集换方言仍 ~100% |

> S3 的"手写计划跑通"是关键节点：它让**执行链路先于 LLM 被验证**。
> 之后模型接进来只是替换计划来源，链路本身已经可信。

## 7. 命名与配置约定

| 项 | 约定 |
|---|---|
| 核心包名 | `nl2sql`（PyPI 未冲突；如需发布再议） |
| 数据源标识 | `source_id`，用户自定义，默认 `"default"` |
| 配置载体 | `NL2SQLConfig`（pydantic），禁止读环境变量做隐式配置 |
| 状态目录 | 默认 `data/`，可在配置里改；测试用临时目录 |
| 版本号 | 核心与壳各自独立版本 |
