# 全局规划

> 写于 S3c + P0 之后。此前的 `docs/01–09` 是**分模块的施工记录**，这一份是**整体判断**：
> 现在到底有什么、还缺什么、按什么顺序补、什么决定不做。
>
> 原则：凡是数字都标明怎么测出来的；凡是判断都写理由。看不清的地方写"看不清"。

---

## 0. 一句话结论

**功能上已经够写一篇"系统设计与实现"了，但证据还不够硬，而且它还没在真数据库上跑过。**

三件事横在"能交"和"能答辩"之间：

1. **只在一个引擎上验过。** 全部 25/30 都是在 SQLite 的一个 810 行小表上得到的。
   题目说的是"查数仓"，而真实数仓基本都是 MySQL / PostgreSQL / ClickHouse。
2. **评测集已经被调试污染。** 同一套 30 题被针对性改了至少 6 轮（17→20→23→24→25）。
   现在的 83.3% 不再是"泛化能力"的估计，而是"在这 30 题上的拟合程度"。
3. **题目里的 LangGraph 还没兑现。** 运行时是手写的工具循环，`build_langgraph` 是一个
   `raise NotImplementedError` 的桩。题面承诺的架构，代码里一个字都没有。

这三件事都不是"再写点代码"能解决的，所以它们排在所有新功能前面。

## 2. 三个目标在拉扯

这个项目同时被三个目标推着走，它们要的东西并不一样：

| 目标 | 要什么 | 冲突点 |
|---|---|---|
| **个人效率工具** | 接上我的真库、快、错了能看懂 | 要真引擎；要流式；要少废话 |
| **毕业论文** | 一个能讲清的技术主张 + 可复现的实验 | 要留出集；要消融；要图表 |
| **可扩展底座** | 加数据源/加能力/加技能都便宜 | 会持续增加表面积 |

**判定标准（后面每个待办都要填）**：它服务上面哪一个？服务不了任何一个就不做。

好消息：三个目标在**"先在真实引擎上跑通"** 这一项上完全重合——
产品要它、论文要它的泛化证据、底座要它证明适配器接口不是纸面上的。

## 3. 五个真缺口（按致命程度排序）

### G1. 只在 SQLite 上跑过 ← ✅ 已解决（M1），且只解决了一半

> **事后核对（M1 完成时补记）**：这张表当初是"按可能崩的顺序"猜的。实际跑完 MySQL 后：
> `identifier_quote` **第一次跑第二个值就通了**（反引号），抽象是够的；
> 只读、元数据两行如预测那样需要引擎专属实现，都做成了；
> **日期分桶如预测那样炸了**——C3 的 `strftime` 在 MySQL 上报
> `(1305, 'FUNCTION nl2sql_golden.strftime does not exist')`，成为"时间粒度要成为一等公民"（M3）
> 的实证；字符串聚合这条黄金集没有需求，没被验证过，仍算未证实。
> 结论：**30 题里 29 题跨引擎结果集逐题一致**，唯一不一致的就是这一行预测的那件事。
> 详见 `docs/11`。

SQLite 是最宽容的引擎：没有类型校验、日期就是字符串、`"x"` 与 `` `x` `` 都收。
真实数仓的差异是成片出现的，而且**有一半的抽象已经在了、只是从没被第二个实现验证过**：

| 差异点 | 抽象在不在 | 现状 | 后果 |
|---|---|---|---|
| 标识符引号 | ✅ `SourceCapabilities.identifier_quote` | 编译器确实从能力读（`dialect/__init__.py:1041`），SQLite 声明 `'"'` | 路径**存在**，但从没跑过第二个值。这类"只有一个实现"的接口，最容易在第二个实现上崩 |
| 只读 | ❌ | SQLite 靠 `?mode=ro` URI | MySQL 得靠 `START TRANSACTION READ ONLY`；守门要按引擎实现，不能只改 URI |
| 元数据 | ✅ `SnapshotMeta` / `ColumnMeta.generated` | `PRAGMA table_xinfo` | MySQL 走 `information_schema.COLUMNS`，生成列在 `EXTRA` 里是 `STORED GENERATED` |
| 日期分桶 | ❌ | `month` 维度直接写成 `expr="substr(f.order_date, 1, 7)"`（`golden_model.py:77`） | **语义模型里嵌了引擎专用 SQL**，换个引擎所有时间维度全废 |
| 字符串聚合 | ❌ | `GROUP_CONCAT(x)` | MySQL 语法里分隔符是 `SEPARATOR ','`，方言副本 |

表格里"抽象在不在"这一列是关键：`identifier_quote` 已经上了一条从没被验证的分支，
而日期分桶是**根本没有抽象**——它把 SQLite 语法直接焊进了语义模型。
后者是阶段 2 要做"时间粒度作为维度属性"的真正原因，不只是为了答 C3 一题。

`pymysql` 与 `mysql.connector` **已安装**；`SourceConfig.validate()` 的 `mysql` 分支已写校验；
`nl2sql/sources/__init__.py` 的注释写着"MysqlAdapter 在 S8 注册"，扩展点是 `registry.adapters`。
所以缺的确实只是 `nl2sql/sources/mysql.py` 一个文件 + 一次注册。

**M1 实际做的事**：写了那个文件、把它注册进 `_BUILTIN`、把黄金集灌进本机 MySQL 8.0.26
（`nl2sql_golden` 库，810 单 / 1315071.00 元，与 SQLite 逐值相同）、另建只读账号
`nl2sql_ro` 作为第三道防线、写 `tests/test_m1_mysql.py` 六节验收。
过程中修掉两份判分器口径不一致（详见 `docs/11` §4）——这是 M1 最意外的收获：
**跨引擎验收顺便把"我们自己判分不严"这件事查出来了**。

### G2. 评测集已被调试污染 ← 最伤论文

同一套 30 题被针对性改了至少 6 轮。每一轮都是"看哪题错 → 改规划器 → 重跑"。
这在工程上完全正确，在**测量**上是灾难：

- 30 题里 1 题 = 3.3 个百分点，25 与 26 的差别没有意义
- 改过的地方都变好了，没改过的地方（F 类只有 2 题）被系统性低估
- 无法回答答辩最可能问的那句："换个数据集还行吗？"

**修法不是"再调准一点"，是"另写一套没看过的"**：新写 20 题（同一张表、不同问法），
开发期不跑、只在里程碑跑。成本半天，收益是把"83.3%"从拟合度变回估计值。

### G3. 没有历史 —— ✅ 已解决（M1 第一件）

`git init` + 首次提交已于 2026-10-21 完成，当前 3 个提交：

首次提交 140 个文件 / 37564 行。同时做了两件配套的事：

原先这里的判断（"不做一定后悔"）成立，并且已经兑现。

### G4. 语义层还缺两个"类"

已知 5 个失败里，有 2 个不是"调参问题"，而是**缺原语**：

| 缺口 | 表现 | 正确修法（不是打补丁） |
|---|---|---|
| **时间粒度不是一等公民** | C3（ISO 周）答不了，因为 `month` 只是 `substr(order_date,1,7)` 一个写死的维度 | 把 `grain: day/week/month/quarter` 声明成维度属性，编译期按方言展开。一个机制覆盖所有粒度，顺带修掉"换个粒度就要加一个维度" |
| **没有"与全表聚合比较"的原语** | F1（高于平均消费的客户）规划不出来 | 加一个标量比较节点：`Compare(measure, against=<全表聚合>, op, factor)`。这是分析场景里极常见的一类（高于平均、占前 10%、超过总体的 X%） |

两个都契合项目已有套路：**契约 → 编译器 → 规划器 → Prompt → 黄金计划 → 测试**，
前面已经用这套流程加过 `having` / `qualify` / `pivot`，第三次做会更快。

而且它们正好是**论文里最好讲的一段**：怎么判断一个失败是"缺能力"还是"缺调参"，
以及怎么用同一个流程加原语而不打补丁。

#### 5 个失败题逐个处置

| 题 | 失败形态 | 处置 | 归属 |
|---|---|---|---|
| A3 | 跑通但结果不符 | `paid_order_count` 同义词表补「几笔/几单」 | 调参（10 分钟） |
| B6 | 跑通但结果不符 | 比率问句的组成项剪枝（`ratio` 的分子分母不该同时当度量输出） | 调参（半天） |
| D3 | 多输出一列「客户数」 | 规划器不该在用户没点名时擅自加维度 | 调参（半天） |
| C3 | 跑通但结果不符 | **时间粒度原语** | 原语（阶段 2） |
| F1 | 规划不出来（`UNRESOLVED`） | **标量比较原语** | 原语（阶段 2） |

三个调参、两个原语。调参那三个**建议放到最后做**——它们只服务黄金集，
而阶段 2 的原语会顺带改变规划器行为，先调可能白调。

### G5. 可观测性与体验

- **无流式**：带模型的路径实测 3–9 秒（插件试炼里 agent 跑了 9.4 秒）。9 秒空白页面在个人工具里是致命的。
  > ✅ **M2 已解决**（实测首字节 <0.5s，`GET /api/query/stream`）。
  > 但解决方式与当初的预期**不同**：当初以为要靠 LangGraph 的 `astream_events`，
  > 实际发现那会把"循环执行器"排除在流式之外——而两条路的行为必须等价。
  > 最后是**单步状态机自己发事件、执行器只转发**，两条路的事件流逐字相同。
  > 教训：先想清楚"等价性"是硬约束，再选实现手段；反过来会得到一个
  > "图执行器有流式、循环执行器没有"的半成品。
- **失败归因的"词汇表"已经有了，缺的是"汇总"**：`contracts/pipeline.py` 里的 `QueryStatus`
  已经是九种状态（`ok / empty / truncated / unresolved / invalid_sql / blocked / timeout / error / need_clarification`），
  `cache.stats()` 也在。缺的是**把它们聚起来**——按状态、按工具、按时间出数。
  这一块的成本比看上去低得多，因为它不是"设计一套归因"，只是"把已有的数加出来"。
- **无工具级统计**：说不清"这个工具用过几次、失败率多少、平均多久"。
  做 P1 技能效果评估时这是前置条件（否则"技能有没有用"只能靠感觉）。

## 4. 论文该讲什么

### 4.0 题目已定（m01600）

> **基于LangGraph智能体的NL2SQL数据仓库辅助查询系统设计与实现**

六个月（约到 2027-04）。这两条改变了下面的判断，逐条说明。

**先说一处推翻。** 本文档初稿把"用 LangGraph 重写运行时"列进了**不做清单**，
理由是"当前运行时已被完整测量，换运行时没有可测收益"。
题目定了 LangGraph，这条**作废**——架构是论文的门面，不能因为工程上不必然而删掉。

但那个理由并不是废话，它变成了**义务**：题目承诺了 LangGraph，
答辩时第一个问题必然是"为什么非它不可"。答不上来，架构选择就是减分项。
所以这一章必须**量化地**回答它（见 §4.3），而不是"因为它有状态图"。

**好消息：这不是重写。** 契约早已为它留好位置，缺的只是一个执行器：

| 已经存在的 | 位置 |
|---|---|
| `NodeSpec` / `Edge` / `GraphSpec` | `nl2sql/contracts/pipeline.py` |
| `PipelineNode` Protocol（`run(state) -> state`） | 同上 |
| `GraphState = dict[str, Any]` + 状态键约定 | 同上 |
| `build_default_graph()` 返回真实 GraphSpec | `nl2sql/agent/__init__.py:33` |
| `AgentGraph(spec, ...)` 已按 GraphSpec 跑 | `nl2sql/agent/__init__.py:53` |
| `build_langgraph(spec, nodes)` **桩**（`raise NotImplementedError("S4")`） | `nl2sql/agent/graph.py` |
| `langgraph 1.2.1` / `langchain 1.3.1` | 已安装 |

也就是说：**"一套契约 + 两个执行器"** 这个结构本来就在，只是第二个执行器没写。
这反而成了论文里最漂亮的一段设计叙述——不是因为需求才引入框架，
而是因为契约先留了缝，框架后来才被填进去，并且**填进去之后行为可以逐题比对**。

### 4.1 主线：LangGraph 编排 + 语义层约束

题目定了"LangGraph 智能体"，所以架构叙述就是 LangGraph。
但**真正的技术贡献不在编排框架上**——编排换谁都能做，真正被测量出来的是另一件事：

> **确定性 NL2SQL 的准确率上限由语义层对问题的覆盖率决定，而不是由模型强弱决定。**
> 当覆盖率不足时，LLM 的优势是**绕过语义层现编 SQL**，而不是"理解得更好"——
> 这个绕过是有代价的，代价可以量化。

两者不冲突，是**分工**：

| 章 | 讲什么 | 什么证据支撑 |
|---|---|---|
| 架构章 | 基于 LangGraph 的可替换编排：契约 → 图 → 两个执行器 | 行为等价逐题一致 + 首字节时间 |
| 方法章 | 语义层约束的双规划器（规则 / 模型 / 混合） | 四种规划器实测 |
| 实验章 | **覆盖率是上限，绕过有代价** | 覆盖率扫描 + 口径漂移 |

**不要**把"基于大模型"当卖点——实测规则规划器反超（M4 覆盖率三档
rule 29/24/20 对 llm 23/20/17；留出集 13/20 对 12/20），拿模型当卖点会被
自己的数据打脸。标题里的"智能体"落在**工具循环 + 图编排**上，
这一点站得住：模型自主选工具、输出结构化决策、图上有条件边与循环。

### 4.2 支撑它的四个实验（都不贵）

**实验一：覆盖率扫描（核心）**

把语义模型分三档裁掉（满配 17 指标 / 中配 11 / 低配 5），每档都跑 rule 与 llm。
计划时的预期与**实测**（M4 已完成，详见 `docs/14` §2）：

| 档位 | 计划预期 | 实测（rule / llm / 语义天花板） |
|---|---|---|
| 满配 | rule 25/30 | **29 / 23 / 30**（rule 差 1 题是已知的 D3 口径不一致） |
| 中配 | 显著下降（缺指标 → **规划不出来**） | **24 / 20 / 25**（rule 失败 6 题**全部 `status=ok`**） |
| 低配 | 继续下降 | **20 / 17 / 21**（rule 失败 10 题里 9 题 `status=ok`） |

要记录的不只是准确率，还有**失败类型**。计划时的预判是：
rule 大多 `UNRESOLVED`（诚实认输），llm 大多"跑通了但口径不对"（**看起来成功了**）。

**实测把这个预判推翻了一半**：缺覆盖时规则规划器也大多"跑通但答案不对"——
因为指标匹配是部分匹配，问句里总有词能落到剩余指标上。于是真正的结论变成：

> **失败不可见不是模型规划器的特性，而是"语义层覆盖不足"这个状态本身的性质。**
> 换掉规划器不会让失败变得可见，只是换一种"看起来成功"。

**模型档（llm）补跑后，方向性结论也确定**：三档 23/20/17 全部低于 rule，
且 llm 多出 `EXEC_ERROR` / `COMPILE_FAILED` / `UNRESOLVED` 一类"没产出结果"
的失败（满配 7 个失败里 1+1，中低配各再多 2 个编译失败）。模型能绕过语义层
现编 SQL，但"能绕过"不等于"结果可控"——它把一部分"规划不出来"换成了
"写出来、跑得过、数字不对"。单次测量 + 模型输出非确定（docs/12 §3.2），
llm 数字只作量级参考。

成本：rule 部分 8 档 × 30 题全离线，秒级完成；llm 部分 3 档 × 30 题
≈ 90 次模型调用（约 2 分钟），已于 2026-10 补跑。

**实验二：口径漂移（已在真实对话里抓到一次）**

同一句"2024 上半年实收金额"，原记录是：

- 走语义层 `net_revenue`：**161826.97**
- agent 自己写 `SUM(f.amount)`：**194758**

差 **20.4%**，因为后者忽略了退款/未支付。这不是假设，是 T 系列调试时真实发生的。
M4 做这个实验时核对发现：**161826.97 其实是客户"冯超"的实收金额，不是全渠道**
（2024H1 全渠道语义层是 991991.77，naive 是 1315071，差 32.6%）。样本本身是真的
（`docs/05` §③ 有原始记录），所以按"冯超"重建 DR1，全渠道口径另外补一例。
**数字错了要改记录，而不是把记录凑成数字。**

M4 实测（`docs/14` §3）：脚本化 13 例，**13/13 偏差 > 5%，中位 22.5%，
最大 66.5 倍**（把订单行数当客户数）。一张"绕过语义层的代价"表已经进 `docs/14`。

**实验三：留出集**

新写 20 题，开发期不跑，最后跑一次。哪怕掉到 70%，如实写，
"留出集 70% / 训练集 83%" 比"83.3%"诚实得多，也更能说明方法有效（差距小 = 没过度拟合）。

**M4 实测**：留出集 **13/20 = 65.0%**（rule）、**12/20 = 60.0%**（llm）——
两个规划器都远低于黄金集 96.7%，说明**开发集数字不能外推**；rule 的 7 个失败
**全部 `status=ok`**，6 个连行数都对、只有数字错。跑完没有据此调参——
否则留出集就变成了训练集。详见 `docs/14` §5。

**实验四：运行时等价与首字节**

两个执行器跑同一批问题，比 outcome（`status` / `answer` / 工具调用序列）；
同时量"从请求到用户看到第一个字"的时间。这是 §4.3 的数字来源。

### 4.3 LangGraph 这一章要怎么讲才有分量

答辩会问"为什么非 LangGraph 不可"。**必须用数字回答，四条：**

| 论证点 | 怎么量 | 预期 |
|---|---|---|
| **流式**：手写循环一次性返回，用户 9 秒看白屏 | 首字节时间（ttfb） | 9.4s → <1s |
| **可替换**：执行器换掉，行为不变 | 同批问题 outcome 逐题比对 | 0 差异 |
| **可恢复**：中断后从上次状态继续 | checkpointer 恢复后是否重复调用工具 | 0 重复 |
| **可解释**：图能画出来 | 直接导出 mermaid/png 作论文插图 | 手写循环给不出 |

**如果这四条量化不出来，LangGraph 就只是装饰。** 所以 M2 的验收标准写成数字，不写"跑通了"。

**已知的一个技术难点**（要写进设计章，说明"框架细节不外溢"）：
LangGraph 1.x 的 state 是 `TypedDict` + reducer，
而本项目的契约要求 `GraphState = dict[str, Any]`、节点签名 `run(state) -> state`（整份覆盖写）。
两者语义不同。做法是**在适配层内部**定义一个本地 `TypedDict` 并写 reducer，
把"整份覆盖"适配成"覆盖写"，`contracts/` 不引入 langgraph 一个字符。
这也是层约束检查能过（`nl2sql/` 不得 import 框架）的前提。

### 4.4 明确不主张的

- 不说"准确率超过 SOTA"——只有 30 题 + 20 题留出，没有可比基线
- 不说"支持多数据源"——M1 之后是两个引擎，写"两个引擎验证了适配抽象"，不写"支持"
- 不说"用 RAG 提升准确率"——**实测贡献 0 题**，这个负结果要写进论文，它比假的正结果有价值
- 不说"多智能体"——是一个带工具循环的智能体，不是多智能体系统

**与计划的两处实质偏离，都是有理由的**：

1. **节点不是 `call_tool` / `observe` / `answer` 三段**。原计划是把工具调用与观察
   拆成两个节点，但 7 道护栏（打转、空数据、叙述式回答、延迟承诺……）必须
   **在工具返回之后、下一轮决策之前**统一判断，拆成两节点反而要在两处各判一次。
   所以 `act` 一个节点做完"调工具 + 观察 + 选更丰富结果"，护栏集中成 `review` 节点。
2. **SSE 不用 `astream_events`**。`astream_events` 只有图执行器有；循环执行器没有，
   那样两条路的界面行为必然不同——而 M2 的验收标准是"等价"。
   改成**由 `AgentCore` 发事件、执行器只转发**：两条路的事件流逐字相同
   （测试里就是比这个），SSE 端点对执行器无感知。

**风险兑现情况**：计划里担心的"reducer 与整份 state 冲突"没有发生——因为没有用
reducer，状态是纯 dict、节点返回部分字段。真正的坑在别处：LangGraph 按**签名注解**
决定要不要注入 `config`（`Any` 会被当成"不要 config"），以及 Starlette 的
`TestClient` 会把整个 SSE 响应缓冲完再交给调用方（首字节必须用真 uvicorn 量）。
两条都写进了 `docs/12` §5。

**止退条件没有触发**：等价性验收通过，但**默认值仍是 `auto`（装了 langgraph 才用图）**，
不是硬编码成 `langgraph`。理由：`loop` 是零依赖的等价性基准，
把它留在默认路径上，才能随时回答"是不是框架本身带来的差异"。

**与计划的三处偏离，都是有理由的**：

1. **`pivot+having` / `pivot+qualify` 没有解开**。pivot 之后的结果是"桶宽表"，
   HAVING 要过滤的是内层聚合值还是外层桶列、qualify 的窗口要在哪一层开，字段
   语义和新 SQL 形状都得先定义。为了过验收线写一个"看起来支持"的假机制，比
   不做更糟——所以保留明确报错，把这一条移到 M4 之后评估。
2. **`against` 的取值从计划里的 `"all" | "group"` 改成 `"all" | "result"`**。
   "group" 会让人以为"按维度分组内的平均"（那需要 PARTITION BY），而真正要
   区分的是"整表平均"与"当前结果集（已过滤）平均"。名字改对，歧义才真的
   变成参数。
3. **`quarter`/`year` 只有映射、没有题验证**。映射表和 `_GRAIN_WORDS` 都有，
   但黄金集里没有对应问法，端到端路径未验证（只测了"未知粒度会报错"）。
   留出集也没造这两类题——不想在 M3 收尾时用新题制造"看似验证"。

**风险兑现情况**：计划里担心的"方言函数写进语义文件"用"声明与展开分离"
解决了；真正的坑在别处——规划器会**修改共享语义模型**（条件聚合指标
`extend_metrics`），而 B6 的比率剪枝用了位置启发式，于是同一道题在"问过
别的题之后"从 2 列变 4 列。单题测试永远绿，序列测试才抓得住。这条写进了
`docs/13` §4，并成为 `tests/test_m3_semantics.py` 的 [E] 段。

| `docs/14-实验.md` | 五个实验（计划四个 + 补的消融）+ 五张表 + 一条曲线 + 限制与复现命令 | ✅ |

**与计划的四处偏离，都是有理由的**：

1. **多做了一个消融实验**。原计划四实验里没有消融，但"各组件贡献什么"是答辩必问，
   而且成本极低（六组 × 30 题 = 秒级），所以补成第五个实验。代价是"四张表 +
   一张曲线"变成了"五张表 + 一张曲线"——这是超交付，不是缩水。
2. **llm 档从"未跑"变成"补跑后成了反例"**。原计划"三档 × 两规划器"，
   一开始因无 Key 只跑 rule，JSON/表格显式 `skipped`、不写成通过；
   补跑后结果比预期更有信息量：**规划器升级不提高准确率**（23/20/17 vs
   rule 29/24/20），说明瓶颈在语义层覆盖与问法覆盖，不在规划器能力。
   模型档只跑一遍（模型非确定），因此不做细粒度题间比较。
3. **漂移的 naive 侧是人工复现的典型错误**，不是模型真实输出。它证明"典型错误
   写法会造成多大偏差"，但不能代替"模型漂移分布"；后者可以后续用 llm 规划器
   补，当前未做。这条限制写进了 `docs/14` §8。
4. **DR1 的口径做了自我纠错**。原记录"161826.97 vs 194758 = 20.4%"里的
   161826.97 实际是"冯超"个人实收金额，不是全渠道；按真实样本重建 DR1，
   另补 DR13（全渠道 991991.77 vs 1315071）。如实写进 `docs/14` §3.3。

**风险兑现情况**：计划里最担心的是"实验做得太晚，数字站不住"。实际结果比预期
**更强**：覆盖率曲线的 0–1 题差距把"瓶颈是语义层表达力"从单点结论变成了曲线证据；
但也**更难看**：留出集只有 65.0%，与黄金集 96.7% 差 31.7 个百分点。两个数字都
如实写——`docs/14` 的立场是"开发集数字不能外推"，而不是"挑好看的数字进论文"。

**与计划的三处偏离，都是有理由的**：

1. **统计没有复用 `history` 表，而是新建两张**。`history` 是回放契约
   （`sql`/`plan_fingerprint`/`error_message`），观测要的是可索引的
   `planner`/`runtime`/`steps`/`cached`——混表会让两边加字段互相绑架。
   统计走自己的时间/状态索引，回放不受影响。
2. **工具统计只在 agent 模式有数据**。线性管线（`rule`/`llm`/`hybrid`）
   不经过工具循环，`tool_log` 天然为 0。这不是 bug，是模式差异；
   `docs/15` §2 与 §8 都写明了，否则试用时会被当成故障。
3. **统计口径做了三个"反直觉"决定并写进契约测试**：`empty`/`truncated`
   算 success（数据事实不是系统失败）；`need_clarification` 单列、不算失败
   （把追问算进失败率会让"主动澄清"看起来像出错）；延迟分位用最近秩法
   （小样本插值会报出不存在的耗时）。这类口径一旦漂移，失败率会**悄悄变低**。

| **NoSQL 数据源** | 用户最初提过，但"SQL 语义模型"对 NoSQL 没有对应物。要做只能是 SQL-over-NoSQL（把 Mongo 映射成表），那是另一个课题。论文里如实写边界 |
