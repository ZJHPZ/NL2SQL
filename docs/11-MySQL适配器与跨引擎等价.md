# 11 · MySQL 适配器与跨引擎等价（M1）

> 这一章记录 M1：把引擎从"只有 SQLite"变成"两个引擎共用同一套上层"，
> 并用 30 题逐题比对证明**上层真的没有依赖 SQLite**。
>
> 结论先放这里：**29/30 逐题一致**，唯一不一致的 C3 是当初就预测会炸的日期分桶，
> 它被正确地留给了 M3（时间粒度作为一等公民），而不是在 M1 里用
> `DATE_FORMAT` 打个补丁糊过去。
>
> 更有价值的副产品不是适配器本身，而是**发现我们自己的判分器有两份、口径不一致、
> 其中一份还会崩**（§4）。跨引擎验收顺便把"测量工具本身不可信"这件事查出来了。

---

## 1. 为什么第二个引擎便宜，而"验证"不便宜

`docs/10` §3 G1 当时估的成本是：**一个新文件 + 一次注册**。这个估计基本准：

| 部分 | 实际工作量 |
|---|---|
| `nl2sql/sources/mysql.py`（389 行） | 半天。大部分内容是错误码提示与值归一化，不是 SQL |
| 注册进 `build_adapter` | 10 行 |
| 数据搬迁脚本 | 半天（但很值，见 §3） |
| 只读账号脚本 | 1 小时 |
| **等价性验收 + 查出来的问题** | **一天半，占了 M1 一大半** |

也就是说：**做适配器便宜，证明适配器是对的贵**。
这个比例在论文里是能写的——"可替换"如果只做到"跑通一次"，成本确实很低；
要能说"换了引擎行为不变"，就得把 30 题跑两遍并解释每一处差异。

## 2. 适配器四层

`nl2sql/sources/mysql.py` 的 docstring 里写了同样四层，这里解释"为什么是这四层"。

### 2.1 能力声明：`identifier_quote` 第一次真正被使用

`SourceCapabilities.identifier_quote` 一直存在（`nl2sql/contracts/source.py:29`，默认 `'"'`），
编译器也确实从能力读（`nl2sql/dialect/__init__.py:1041`，
`quote = self._cap.identifier_quote or ""`）——但在此之前**只有 SQLite 一个实现**，
等于这条分支从没被执行过。

MySQL 声明 `` identifier_quote="`" ``，第一次跑就通了。
这是 G1 表格里唯一一条"抽象已经在了、第二个实现直接可用"的行。

**教训（正面的）**：把引擎差异表达成**数据**（能力声明）而不是**代码分支**，
第一个实现上看起来是"过度设计"，第二个实现上就是"零成本"。
但这个判断只有在第二个实现之后才成立，事前只能说"值得赌"。

### 2.2 只读：三层，且互相独立

| 层 | 机制 | 失效时会怎样 |
|---|---|---|
| 1 | `guard` 文本校验（解析 AST / 白名单） | 解析器有绕过手法就能过 |
| 2 | `START TRANSACTION READ ONLY` | 一旦忘了开事务就没了 |
| 3 | 数据库账号 `nl2sql_ro` 只有 `SELECT` | 无 |

第 3 层的价值在于：**它不依赖我们的代码正确**。前两层写错都可能被绕过，
第 3 层是库自己在拒绝。论文安全章里"我们的正则很严格"没有说服力，
"即使守门被绕过，库也不让写"有。

主链路从灌完数那一刻起就一直跑在 `nl2sql_ro` 下——
不是"设计上应该只读"，而是**开发期从未用 root 跑过查询**。

### 2.3 超时：`max_execution_time`，以及降级要留痕

```sql
SET SESSION max_execution_time = <毫秒>
```

MySQL 8 支持会话级执行时间上限。设失败（老版本 / 权限）时**不能让查询失败**，
于是降级到驱动的 `read_timeout`，同时把 `_timeout_fallback = True` 记在适配器上。

**为什么留痕**：降级之后超时语义变了（`read_timeout` 是网络读超时，
不是引擎侧中断，服务端可能还在跑）。这种"能跑但语义变弱"的降级如果不记录，
排障时会被误判成"超时没生效"。

### 2.4 值归一化：在适配器做，不在上层做

`_normalize()` 把驱动返回的对象转成"可直接 JSON 序列化、可直接比较"的基本类型：

| 驱动返回 | 归一化为 | 为什么 |
|---|---|---|
| `Decimal` | `float` | 判分器按数值容差比；`Decimal` 与 `float` 混比会抛 `TypeError` |
| `datetime` | `isoformat(sep=" ", timespec="seconds")` | 与 SQLite 的 TEXT 表示对齐 |
| `date` | `isoformat()` | 同上 |
| `bytes` | utf-8 decode | 列里有二进制时不要整行崩 |

**做在适配器的理由**：这是"引擎的物理表示"与"上层的逻辑值"之间的边界。
放在上层就意味着每个消费方都要处理一遍 `Decimal`，漏一处就是运行时异常。
放在适配器只有一个地方要写对，而且**能被 A 节那 13 条契约检查逐条盯住**。

### 2.5 元数据：生成列在 `EXTRA` 里

SQLite 用 `PRAGMA table_xinfo`，生成列的特征是 `hidden in (2, 3)`。
MySQL 走 `information_schema.COLUMNS`，生成列的特征是 `EXTRA` 里含 `GENERATED`
（`STORED GENERATED` / `VIRTUAL GENERATED`）。

这两套元数据在 B 节被逐字段比对过：5 张表的列集合、可空性、主键、生成列标记、
列序号、外键、行数**全部一致**。类型名不一致（`INT/INTEGER`、`DECIMAL/REAL`、
`DATE/TEXT`）**只报告不断言**——因为"类型名不同"是事实而非缺陷，
钉死它只会让以后加引擎时到处报假警。

### 2.6 错误码翻译

`_ERROR_HINTS` 覆盖 6 个码：1064（语法）、1146（表不存在）、1054（列不存在）、
1142（权限拒绝）、1305（函数不存在）、1792（只读事务里写）。
3024 / 2013 被判为 `QueryTimeoutError`（前者是引擎侧超时，后者是连接中断）。

**为什么值这点代码**：这套系统的主要用户是"不会写 SQL 的人"，
原始错误 `(1146, "Table 'nl2sql_golden.dim_channl' doesn't exist")` 对他没有用。
翻译成"表 `dim_channl` 不存在，可用的是 `dim_channel`"才是可行动的。
这件事在插件试炼那一轮（`docs/04`）已经被证明过一次：错误提示不可行动，
等于没有。

## 3. 数据等价：为什么不重跑 `seed_data.py`

把 SQLite 的行**原样搬**进 MySQL（`scripts/mysql_load_golden.py`），
而不是在 MySQL 上重跑造数脚本。

**理由**：两套造数逻辑一旦分叉（比如一边用了 `random` 没固定种子、一边改了小数处理），
"等价性验收"的前提就没了——你比的是两个引擎，还是两个数据集？分不清。

搬到 MySQL 时刻意的三种差异（`golden_set/schema_mysql.sql`）：

| 项 | SQLite | MySQL | 为什么故意不同 |
|---|---|---|---|
| 日期 | `TEXT` | `DATE` | 真实数仓就是这么存的；也正好能暴露"日期当字符串用"的代码 |
| 金额 | `REAL` | `DECIMAL(12,2)` | 同上；驱动会返回 `Decimal`，逼出 §2.4 |
| `amount` | `STORED` 生成列 | `GENERATED ALWAYS AS (...) STORED` | 验证生成列元数据在两边都识别得出 |

`DECIMAL(12,2)` 会不会丢精度？**实测不丢**：黄金集三列金额
（`unit_price` / `discount_amount` / `amount`）全部恰好两位小数，
`MAX(ABS(x - ROUND(x, 2))) = 0`。这个断言是"用 DECIMAL 无损"的前提，
不做这一步就只是相信。

灌数后逐项核对：`dim_date 182 / dim_customer 12 / dim_product 16 / dim_channel 5 /
fact_order 810`，数量合计 **1462**，金额合计 **1315071.00**，优惠合计 **92462.10**，
状态分布 `{'已支付': 661, '已退款': 73, '已取消': 76}` —— 与 SQLite 逐值相同。

文件头特意写了一句话：

> 语义层里写死 `substr(f.order_date, 1, 7)` 的月维度在 MySQL 上不会报错，
> 会返回错的值。

这是 M3 的真正动机，见 §7。

## 4. 判分器漂移 ← 本轮最重要的发现

跨引擎验收第一次跑，端到端结果是 **MySQL 20/30**，而 SQLite 是 25/30。
第一反应是"适配器有问题"。实际是**判分器有两份，口径不一致**。

### 4.1 两份判分器

| 位置 | 状态 |
|---|---|
| `golden_set/evaluate.py: rows_equal()` | 权威版本，被 `evaluate.py` 主流程用 |
| `scripts/compare_planners.py: rows_match()` | 自带的最小实现，注释写着"从 tests 导入会触发 stdout 包装" |

两份对 **A4 / B1 / D2 / D6 / E4 五道题给出相反结论**：
`rows_equal` 说错（20/30），`rows_match` 说对（25/30）。

### 4.2 谁才是错的：严的那个

直觉会认为"权威版本严、自带版本松，所以 25/30 掺了水"。**查下来正好相反。**

`rows_equal` 的 `canon_rows` 有两条实现不完整：

1. **只把字符串列排序，数值列保持原序**：
   `strs = tuple(sorted(c[1] for c in cells if c[0] != "num"))`
   —— 于是同一行里两个数值列互换会被判成不同，而两个字符串列互换会被判成相同。
   同一份口径，一半宽松一半严格。
2. **遇到 NULL 直接崩**：同一个表达式对 `("null",)` 这种单元素元组取 `c[1]`
   → `IndexError`。也就是**结果里出现 NULL 必然崩**，只是黄金集恰好没这种题。

`rows_match` 排序了数值列（在这一条上是对的），但它**把 NULL 整个丢掉**
（在这一条上是错的）。

所以那 5 道题的相反结论是：**`rows_equal` 判错（过严），`rows_match` 判对**。
20/30 是**低估**，25/30 才是当时的真实水平。

> 这两件事放在一起才是真正的教训：**两边各有一条实现得不完整**，
> 于是差异看起来像"严格 vs 宽松"的对立，实际是"两个都不完整的实现"。
> 如果只问"谁的数字更保守"，就会把正确的那个改坏。

### 4.3 决定：口径只保留一份

`compare_planners.py` 改成 `from evaluate import rows_equal`（`sys.path` 加 `golden_set`），
`rows_match = rows_equal`（保留别名，不留下"两套"的余地）。
`canon_rows` 补上数值列排序与 NULL 处理。三条规则一起写清：

| 规则 | 理由 |
|---|---|
| **行序无关** | SQL 不加 `ORDER BY` 时行序不保证；黄金集的题有很多没写 `ORDER BY` |
| **列序无关**（行内单元格排序，含数值列） | 见下 |
| **NULL 参与比较**（多一列 NULL 不算对） | 见下 |

**为什么列序无关**：判分不比列名（Execution Accuracy 的常规做法）。
不比列名就没有列身份，剩下的只有位置；而位置由 SQL 的书写顺序决定，
与"算得对不对"无关。"列出地区和各地区客户数"里，先写地区还是先写客户数，
语义完全一样。既然不比名字，就应该把行内单元格排序后比。

**为什么 NULL 要算**：如果 NULL 不算，"多输出一列（这一列恰好是 NULL）"
就成了正确答案 —— 这是**漏判**，方向跟宽松相反但同样错。

**代价（诚实记录）**：列序无关会放过一种错误——"两列内容对了但放反了"。
在数据模型里这种错误的后果通常很小（用户看表头就知道），
比"多算了一列数"轻。这个取舍是明确的，不是不知道。

修完重跑：`golden_set/evaluate.py` 自检 **30/30**；
`python scripts/compare_planners.py --planners rule` 仍是 **25/30 = 83.3%**，
失败题 `['A3', 'B6', 'C3', 'D3', 'F1']`，与修之前相同。

> **注意这个"不变"的意思**：修之前 `compare_planners` 报 25/30 用的是
> `rows_match`（松），修之后报 25/30 用的是 `rows_equal`（两处 bug 都补了）。
> 数字没变，**但支撑这个数字的判分器换成了更可靠的那个**。
> 如果只看数字，会以为"什么都没发生"。

> **这条经验可以推广**：同一件事有两份实现，而两份实现只在"出错时才表现不同"，
> 那么不需要犯错，它们也会慢慢分叉。判分器就是典型——它平常不产生输出，
> 没人会盯着它看。**能被两个入口调用的东西，只应有一份实现。**

## 5. 等价性验收：29/30，以及那 1 题为什么不算失败

> **M3 补记**：C3 的缺口已经在 M3 用语义层的 `grain` **正确**闭合，没有在 M1
> 用 `DATE_FORMAT` 打补丁。更新后的数字：C 节 **30/30 逐题一致**；D 节两端
> 都是 29/30，失败题只剩 `D3`（黄金集题面与 SQL 口径不一致，见 `docs/13`）。
> C3 现在在 MySQL 上走 `DATE_FORMAT(order_date, '%Y-%u')`，返回同样的 26 个
> 周桶。下面的原文保留，作为“当时为什么不修”的记录——它记录了一个真发现，
> 也解释了为什么这个坑必须留到 M3。

`tests/test_m1_mysql.py` 六节，A–F 分别测适配器契约、元数据、30 题、端到端、
只读三层、壳层装配。

C 节（30 题逐题比结果集）：**29 equal + 1 known_gap**。
D 节（端到端跑两遍黄金集，规则规划器）：

```
SQLite 25/30 = 83.3%
MySQL  25/30 = 83.3%
失败题（两边相同）: ['A3', 'B6', 'C3', 'D3', 'F1']
```

**这是 M1 的硬验收：不只是通过题数相同，而是失败题目集合逐题相同。**
只比通过数会漏掉"SQLite 错这题、MySQL 错那题"的抵消。

### 那 1 题：C3 的 ISO 周分桶

C3 的逻辑计划里写死了 `strftime('%Y-%W', order_date)`。
在 MySQL 上：

| 账号 | 报错 |
|---|---|
| `root` | `(1305, 'FUNCTION nl2sql_golden.strftime does not exist')` |
| `nl2sql_ro` | `(1142, "execute command denied ...")` |

**同一句 SQL，两个账号报不同的错。** 原因是权限检查先于函数解析：
只读账号没有 `CREATE ROUTINE` 之类的权限，于是在"要不要解析这个函数"之前就被拒了。

**这是一个真发现**：用最小权限账号排障时，会看不到真实的语法/函数错误。
排查这类问题时必须知道这一点，否则会朝着"权限问题"方向查很久。
（同时也说明第 3 层防线确实在生效——它连函数解析都比别人早一步。）

MySQL 的等价写法实测 `DATE_FORMAT(order_date, '%x-%v')` →
`('2024-01', 34), ('2024-02', 27), ('2024-03', 42)`。

**但 `%W` 与 `%v` 并不是同一件事**：`%W` 是"周一为一周之始、00–53"，
`%v` 是 ISO 8601 周（01–53）。把它们当等价物就是在制造一个静默错误——
数字看着像、语义不同。

这正是"按周"必须做成**语义层的 grain**、而不是语义模型里一个 SQL 字符串的真实理由：
一旦是字符串，每个引擎都要各写一遍，而**写错不会报错**。
所以 C3 不是"没做完"，是"这个坑必须在 M3 用正确的方式填"。

**M3 的最终实现**（详见 `docs/13`）：逻辑计划里只有
`dimensions=("week",)` 与 `time_range.grain="week"`，语义文件里只有
`grain: week`，截断表达式由编译器按 `SourceCapabilities.dialect` 展开。
MySQL 侧选的是 `%u`（周一为一周之始、00–53，与 SQLite `%W` 对齐），
**不是** `%x-%v`——M1 已经指出 `%v` 是 ISO 周、语义不同，M3 没有把那个
"看起来像的错答案"抄一遍。黄金计划（`golden_plans.py`）里的 C3 也从
`raw_select` 改成了结构化计划，因此 C 节的逐题等价从 29/30 变成 **30/30**。

## 6. 口令怎么进系统：`credential_ref` 的语义

`SourceConfig.credential_ref` 的语义是**口令去哪取**，不是口令本身。

```
credentials["password"]     显式传入（测试、嵌入式调用）
"env:NL2SQL_MYSQL_PASSWORD" 从环境变量取（生产默认）
"env" / None                取默认变量 NL2SQL_MYSQL_PASSWORD
```

认不出的前缀**报错，不静默退回**。理由与 P0b 的 Prompt 处理同一条：
静默退回会让"我明明配了却没生效"变成最难查的一类问题。

`resolve_secret()` 放在 `nl2sql/sources/__init__.py`，因为"口令从哪来"是装配问题，
不是适配器的问题。适配器只接受一个字符串。

**踩到的坑**：`build_adapter` 里最初写的是 `registry.adapters.get(name)`,
而 `_Registry.get` 在未注册时**抛异常** —— 于是内置工厂永远走不到。
改成 `registry.adapters.has(name)` 再分支。这类"查询式接口用 get 还是 has"
的坑很小，但它会让扩展点静默失效。

## 7. 壳层：换引擎只改一个环境变量

`apps/web/backend/shell_config.py` 增加了：

```
NL2SQL_ADAPTER=sqlite|mysql
NL2SQL_MYSQL_HOST / PORT / USER / DATABASE
NL2SQL_MYSQL_PASSWORD   ← 只从环境读，不进配置文件、不进页面
```

`build_shell_config` 按 `adapter` 走 `add_mysql(...)` 或 `add_sqlite(...)`，
两边都带上 `credential_ref="env:NL2SQL_MYSQL_PASSWORD"`。

F 节验证：改这一个变量 → 装配成 MySQL 数据源 → 无 Key 时退化为规则规划器 →
经壳层问一句能出结果。**上层（规划器 / 编译器 / 守门 / 缓存）一行都没改。**

`raw_env` 里放的是 `NL2SQL_ADAPTER` 与 host/user/database 三项，
**不放口令** —— 页面会展示 `raw_env` 用于排障，口令进去就是泄漏面。

## 8. 这一轮没做的事

| 没做 | 为什么 | 什么时候做 |
|---|---|---|
| C3（ISO 周分桶） | 需要 grain 原语，用 `DATE_FORMAT` 打补丁会制造静默错误 | M3 |
| 字符串聚合（`GROUP_CONCAT` 的 `SEPARATOR`） | 黄金集没有这个需求，**未验证过就不能声称支持** | 有需要时 |
| PostgreSQL | 两个引擎证明"抽象能用"，三个才证明"抽象是对的" | M5 可选 |
| 方言转译（sqlglot） | 现在走"语义层 → 按能力编译"，不是"SQL → SQL" | 不做（见 `docs/10` §6） |
| MySQL 的 `ONLY_FULL_GROUP_BY` 严格性 | 本机 `sql_mode` 恰好没有这一项，所以我们的 SQL 没被这样检验过 | 写进方言章作为已知边界 |

最后一条值得强调：本机 `@@sql_mode = STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION`，
**没有 `ONLY_FULL_GROUP_BY`**。这意味着一些在默认配置的 MySQL 上会报错的
"选了不在 GROUP BY 里的列"的 SQL，在我们这里是能跑的。
**换一台默认配置的服务器就可能全炸。** 这是当前一个真实的、已知的隐患，

## 9. 可复用的教训

1. **把引擎差异表达成数据，不要写成代码分支。** `identifier_quote` 在第一个实现上是
   多余的一行，在第二个实现上是零成本。
2. **判分器只能有一份。** 两处实现只在出错时才表现不同，所以会悄悄分叉，
   而判分器平时不产生任何输出，没人盯着看。
   而且**别用"谁更保守"来选**——这次是两个都不完整，改了正确的那个就会把分数改坏。
3. **数字不变不等于什么都没发生。** 修完判分器后准确率还是 25/30，
   但支撑它的判分器换成了更可靠的那个。只盯数字就会错过这次修正。
4. **只读要用三层，且第三层不依赖自己的代码。** 库账号拒绝是最有说服力的证据。
5. **降级要留痕。** `max_execution_time` 设不上就降级 `read_timeout`，
   但必须记一个标志位，否则"超时语义变弱"这件事没人知道。
6. **等价性要比"失败题目集合"，不只是通过数。** 通过数相同可以是抵消的结果。
7. **最小权限账号会把错误信息变模糊**（1305 → 1142）。排障时先想到这一层。
8. **方言等价物常常不等价**（`%W` vs `%v`）。这类差异不报错，只出错——
   所以必须由语义层统一表达，而不是各处拼 SQL。
