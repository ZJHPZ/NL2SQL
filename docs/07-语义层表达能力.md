# 07 语义层表达能力

这篇记录一次**针对性扩容**：语义层原先只能表达"分组 + 聚合 + 排序 + 取前 N"，
一旦问题要求在**聚合结果之上**再做点什么，就只能走 `raw_select` 逃生通道。

决策依据来自 `docs/02` 第 19 节的两个负结果：

> few-shot 贡献 **0** 题、验证式混合不划算 → 瓶颈在**语义层表达能力**，
> 不在规划器。继续调 Prompt 或加示例是往错的方向使劲。

## 2. 四项能力的契约

四项能力都进 `LogicalPlan`（而不是做成新指标类型）。理由：
**同一份语义模型配合不同的计划构造能回答一族问题**，
不必为每种问法在模型里新增一个指标——否则模型会被问法撑爆。

```python
having:  tuple[Having, ...]    # 分组后的阈值过滤     → SQL HAVING
qualify: tuple[Having, ...]    # 窗口层之后的过滤     → 第三层 WHERE
pivot:   Pivot | None          # 维度取值转成列       → 两层透视
```

窗口能力（累计 / 组内排名）**不新增契约**，用的是已有的 `window` 指标 +
两条新约束。

### 为什么 `having` 不复用 `Filter`

`Filter` 作用在**行**上（WHERE），`Having` 作用在**分组**上（HAVING）。
合成一个类型，编译器就无从判断该放哪一边——放错了不会报错，
只会给出**过滤时机不同**的结果，而且往往看起来合理。

最典型的踩坑：

```
"单个订单成交金额超过 5000 元的订单有几笔？"   → 行级过滤（先筛订单再数）
"实收金额超过 2 万元的品类有哪些？"            → 分组过滤（先求和再筛）
```

同一个"金额超过 N"，一个是 WHERE 一个是 HAVING。规则规划器的判据是
**问句里有没有匹配到分组维度**：有分组维度才是 HAVING。
漏了这条会同时犯两个错——把行级条件升级成分组条件，
**并且删掉原本正确的行级过滤**，结果看着像算出来了。

### `qualify` 与 `having` 的区别是执行时机

```
having   在窗口函数**之前**（作用在 GROUP BY 的结果上）
qualify  在窗口函数**之后**（作用在窗口计算的结果上）
```

所以"每个品类内部销量前 2"必须用 `qualify`：排名要先算出来才知道谁是前 2。
写成 `having` 会得不到结果——那时候"名次"这个列还不存在。

### 为什么透视要分两层

桶条件作用在**明细行**上（决定每行属于哪一列），指标聚合也作用在明细行上。
直接写 `SUM(CASE WHEN <桶> THEN SUM(x) END)` 是嵌套聚合，SQL 非法。所以：

```sql
WITH p AS (                                   -- 内层：按 (分组维度, 桶) 聚合
    SELECT <分组维度>
         , CASE WHEN <桶1条件> THEN '桶1' WHEN <桶2条件> THEN '桶2' END AS __pivot_bucket
         , SUM(<指标>) AS __pivot_value
    FROM ... WHERE <计划过滤> AND (<桶1条件> OR <桶2条件>)
    GROUP BY <分组维度>, CASE WHEN ... END
)
SELECT <分组维度>                              -- 外层：把桶转成列
     , ROUND(SUM(CASE WHEN __pivot_bucket = '桶1' THEN __pivot_value ELSE 0 END), 2) AS "桶1"
     , ROUND(SUM(CASE WHEN __pivot_bucket = '桶2' THEN __pivot_value ELSE 0 END), 2) AS "桶2"
FROM p GROUP BY <分组维度>
```

一个机制覆盖两类问法：

| 问法 | 桶 | 例子 |
|---|---|---|
| 跨期对比 | 时间段条件 | "本月和上月的实收金额分别是多少" |
| 分类转列 | 维度取值 | "线上和线下**各自**的实收金额是多少" |

## 3. 累计与组内排名：语义层声明，规划器挑选

累计指标的定义看起来像在写 SQL，其实不是：

```yaml
- name: cumulative_net_revenue
  label: 累计实收金额
  calculation_method: derived
  expression: >-
    SUM(net_revenue) OVER (ORDER BY month
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
  meta:
    nl2sql: {window: true, decimals: 2}
```

`{{ dimension('month') }}` 里的 `month` 是**分组维度**。两层编译的外层
`FROM agg` 里只有内层产出的列，所以编译器把它解析成 `agg."月份"`。

**规划器不在自己代码里拼窗口 SQL**，而是从语义模型里**找**符合要求的窗口指标：

```python
_find_window_metric(kind="cumulative", base_metric="net_revenue", order_dim="month")
```

方向是"语义层声明能力、规划器选择能力"——加一个新窗口指标不用改规划器。
找不到就让计划退化成普通聚合，而不是生成一个错误的窗口。

### 两条编译期约束（都是"静默出错"的克星）

**① 窗口指标直接引用的维度必须在分组里。**

不检查就会生成外层查不到的 `substr(f.order_date, 1, 7)`，
用户看到的是 `no such column: f.order_date`——从那里反推"要加个维度"太难了。
现在报的是：

```
窗口指标引用的维度不在分组里：cumulative_net_revenue 需要 ['month']。
窗口函数要按维度排序/分区，该维度必须同时出现在 dimensions 中
```

**只查直接引用**：`net_revenue` 内部的 `order_status`/`amount` 是内层的事，
要求它们也进分组会把 6 行变成上百行。

**② 透视的桶条件与计划的时间范围不能约束同一个字段。**

桶已经把时间写死了，再叠一个 `WHERE` 会把上一个窗口整段切掉。
失败方式是"上期那一列恒为 0"而不是报错——**最难查的一类**。
所以直接拒绝而不是悄悄按一种解释执行。

## 4. 一个机制不能有两个真相

分类转列与"取值过滤"共用同一份取值表。这条不是洁癖，是踩出来的：

```python
_VALUE_MAP = {
    "customer_type": [("新客户", ("新客户", "新客")),
                      ("老客户", ("老客户", "老客"))],
}
```

**取值 → 各种写法**，而不是平铺一个列表。平铺会让"新客"和"新客户"
被当成两个不同类别——"新客户和老客户各贡献了多少"于是算出 **4 列**
（新客户/新客/老客户/老客），其中两列是重复的。

同一条规则在两处必须一致：`_match_filters`（"全部取值都出现 → 不是过滤"）
与 `_categorical_pivot`（"全部取值都出现 → 转列"）。
不一致就会出现"先按取值过滤掉、又要按同一取值转列"的荒谬计划——
计划能跑，结果一列全是 0。

### "各自"是必需的，且只认"各自"

"线上和线下的实收金额"既可以按 `channel_type` 分组（12 行），
也可以转成两列（6 行）——**两种都合理**。选错会让结果形状完全变样，
所以只在这类明确的"各自成一列"说法下才转列，否则按分组输出
（信息更多，也更接近"列出明细"的默认预期）。

而且**不能**用"分别"：黄金集里 A2/D2 的"分别是多少"指的是
"不同指标各自的值"，不是"同一维度的不同取值各占一列"。

## 5. 规划器的三处连带修正

扩容之后有三处旧规则被暴露出不够用。它们都不是新功能，是**旧规则与
新能力冲突**：

**① "每个品类前 2" 里的"前2"被同时当成整表 LIMIT。**
两处共用同一段文字，都生效的话"每组前 2"变成"整表取 2 行"——
结果只剩一组，看起来像是分组没生效。现在组内前 N 会显式声明
"这个前N是组内的"，不做整表 LIMIT。

**② "前 N" 没有配排序。**
"前 N / top N"是**排序要求**，不只是行数上限。没有 `ORDER BY` 时
`LIMIT N` 取的是任意 N 行（SQL 不保证顺序），"前5"退化成"随便5行"——
不报错，只是答非所问。

**③ "前N只暗示一个分组维度"的规则砍掉了用户点名的列。**
"销量前5的商品是哪些？**列出商品名称、品类**和销量"里品类是明文要求，
被启发式规则砍掉属于"因为一条经验规则丢掉了明文要求"。
现在如果问句里有"列出"或顿号（中文列清单最直接的两个标记），就不截断。

## 6. 明确不做的两件事

| 缺什么 | 为什么不做 |
|---|---|
| **C3 按 ISO 周分桶** | 要 `strftime('%Y-%W', ...)` 这类方言函数。把它写进指标文件会破坏"这份文件在 dbt 里也能跑"的可移植性（见 `docs/06`）。正确做法是在 dbt 里做一个 `week` 维度（`date_trunc` 或宏），而不是在可移植的语义文件里写死方言 |
| **F1 与全局平均值比较** | `qualify` 目前只支持**字面量**比较。F1 的比较对象是"全部客户的平均消费金额"——一个聚合结果。要做成 `qualify: 实收金额 > 场均` 需要允许比较的右边是一个列引用，那是另一个能力（相等/范围以外的一般化比较），单独做更清楚 |

**留着逃生通道不是失败**。`raw_select` 仍然走守门 / 缓存 / 结果比对，
链路一样被验证。区别只在于：语义层没有真正表达它，
所以模型规划器学不会、也复用不了。

## 8. 验收

```bash
python tests/test_s3c_expressiveness.py
```

盯住的是**每个能力写错会怎样**，而不只是"能跑出数"：

| 组 | 断言 |
|---|---|
| A 指纹 | having/qualify/pivot 都进缓存指纹（否则"带阈值"与"不带阈值"共用缓存） |
| B HAVING | 生成 HAVING 且左边是**聚合表达式**；阈值没跑到 WHERE 里；行级阈值**没有**被误判成分组阈值 |
| C 透视 | 两个桶转两列；数值与基线一致；**桶条件与 time_range 冲突被编译期拒绝**；无条件桶被拒 |
| D 窗口 | 累计按分组维度开窗且单调、末期=各期之和；缺排序维度时报出**缺哪个**；三层结构 `agg → win → 过滤`；名次过滤在窗口层之后；每个分区内名次连续；qualify 列名错时**列出可用列**；维度无别名时不崩 |
| E 收窄 | 语义计划 ≥28、raw_select ≤2，且剩下的两题是**别的**能力缺口 |
| F 端到端 | 七道题由规则规划器直接算出与基线一致的结果 |

另外 `tests/test_s4c_hybrid.py` 里加了一条**防退化**断言：
HAVING / 跨期对比 / 累计 / 组内前N 这四类问法**不再触发模型调用**。
能力悄悄退回"走 freeform"时它会红。

> 顺带修掉一个潜伏的 bug：`SqlCompiler._dimension_sql` 用了
> `PlanDimension.name`（字段实际叫 `dimension`）。黄金集里每个维度都带别名，
> 所以一直没暴露；维度不带别名时直接 `AttributeError`。
> S3c 的 D 段加了一条断言把它钉住。
