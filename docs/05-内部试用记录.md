# 05 内部试用记录

> 在把系统交给别人用之前，我自己先当一次真实用户。
> 跑通测试 ≠ 能当工具用——下面 8 个问题**没有一个来自验收测试**，
> 都是我作为使用者会问的话。

复现方式：

```bash
uvicorn apps.web.backend.main:app --port 8000     # NL2SQL_PLANNER=agent
python scripts/internal_trial.py                  # 跑默认问题集
python scripts/internal_trial.py "自定义问题"
```

试用期间脚本会**先清空结果缓存**——否则改完 Prompt 重跑同一问题会命中
旧结果，让人误以为改动无效（第一次试用就差点被这个骗到）。

## 2. 发现并修复的 6 个问题

### ① schema_brief 从未生效（装配时序错误）

**现象**：问"这个数据库里有什么数据？"，agent 从语义摘要推断出三张维度表，
**漏了 `dim_product`**，事实表只能说"可能的事实表 fact_ 系列"。

**排查**：用真实元数据逐条核对它说的字段——**全对**。所以它不是编造，
而是**信息不完整**。再查 `runtime._schema_brief` 长度 = **0**。

**根因**：`_build_pipeline()` 在 `refresh_snapshot()` **之前**执行，
那时元数据目录还是空的。快照落盘后没有重新同步。

**修复**：`refresh_snapshot()` 末尾调用 `apply_runtime_settings()`。

**效果**：现在能准确列出 5 张表的完整字段与行数，并指出事实表是 `fact_order`。

> 这个问题值得记：验证"模型是不是在编"要用**事实核对**，不能凭印象。
> 我一开始以为它在编，核对后发现是我自己的装配 bug 让它信息不全。

### ② 纠错守卫把正确回答也拦了（守卫死循环）

**现象**：问"消费最高的前5个客户"，agent **已经查出了正确答案**
（冯超/华东/161826.97），却最终报"达到步数上限仍未得出结论"。

**根因**：我加的"承认结果不对却停手"守卫**没有次数限制**。
模型带着说明给出正确回答时也被反复拦下，白烧 8 步。

**修复**：
* 每个纠错守卫**只触发一次**（`_used` 标记）
* 达到步数上限但已拿到有效结果时，**如实说明"结果有效、只是没收敛成结论"**，
  并把结果表交出去——比报"没结论"有用得多

> 教训：纠错提示可以给一次，但不能变成死循环。
> 守卫本身也会成为故障源。

### ③ agent 绕过语义层手写 SQL，导致口径错

**现象**：`消费最高的前5个客户` 返回 **194758**，而语义层口径是 **161826.97**。

**根因**：模型自己写了 `SUM(f.amount)`，**漏掉了"只算已支付"和"减优惠"**。
这比缺表严重得多——语义层存在的全部意义就是保证口径一致。

**修复**：Prompt 增加一节「业务指标必须走语义层，不要自己拼 SQL」，
并**举例说明裸 SQL 会错在哪**：

```
· "实收金额" = 已支付订单 且 金额 − 优惠
· 直接写 SUM(amount) 会把退款和未支付订单也算进去，数字偏大
· 直接写 COUNT(*) 会把取消的订单也算成订单量
```

同时给出**允许手写 SQL 的两种情形**（语义层没覆盖 / 表达不了的形态），
并要求手写时说明原因。

**效果**：同一问题现在用 `SUM(amount - discount_amount) WHERE order_status='已支付'`，
数值正确，且主动附注"该查询为分组内 TopN，语义层无法直接表达，
**但口径与语义层 net_revenue 一致**"。

### ④ 过度探查导致打转中断

**现象**：`上个月各品类的销量对比一下` → 反复调用 `semantic.list_metrics`
**3 次完全相同** → 触发打转保护 → 中断。

**根因**：我写的"可用 `list_metrics` 确认语义层有没有对应指标"
让模型**过度验证**——它明明已从指标清单看到 `quantity_total | 销量`。

**修复**：Prompt 明确「不要反复探查」：

```
semantic.list_metrics 的结果不会两次之间发生变化。
指标清单里的 label（如"销量""实收金额"）就是它的业务名，
用户的说法与 label 匹配即可直接使用，不需要额外验证。
```

### ⑤ 静默替换语义（各城市 → 各地区）

**现象**：问"各城市的销售额"，agent 直接按 `region`（大区）回答，
**没有告知用户替换了维度**。用户会以为看到的是城市数据。

**修复**：Prompt 增加「能被合理理解的问题直接作答，但要写明假设」一节。
现在它明确回答：

```
数据源里没有「城市」这个维度，客户表只提供 region 字段，
实际取值为：华东、华北、华南、西南、华中。
```

> 这条的原则：**可以替换，但必须披露**。静默替换比答不出更危险。

### ⑥ 犹豫时倾向追问，而不是作答

**现象**：`哪个渠道表现最好？` 在两次运行间行为不一致——一次直接回答，
一次追问"您更关注哪个口径"。

**修复**：Prompt 明确「犹豫时选择作答」：

```
· "哪个最好/最差"这类问题，用默认口径直接答（实收金额降序），
  并在回答里写明"这里以实收金额为表现标准"
· "最近"这类相对时间，若上下文里有时间锚点就按它理解，并写明用的哪段时间
· 只有完全无法判断用户要什么（如"卖了多少？"）才追问

为什么倾向作答：追问要等用户一轮，而用户往往只是想"先看一眼"。
给出带明确假设的答案，比让用户再打一遍字更有用。
```

**效果**：`最近卖得怎么样？` 现在答：

```
以数据中最近的完整月份 2024年6月 来看：
  实收金额 171,907.99 元 / 有效订单数 113 笔 / 毛利率 27.3%
说明：这里的"最近"取数据中最新月份（2024-06-30 截止）；
      "实收金额"口径为已支付订单成交金额减去优惠，不含退款与取消。
```

## 4. 一个方法论收获

**"跑通测试"与"能当工具用"之间隔着的东西，只有自己当用户才能发现。**

这批问题里，验收测试一个都覆盖不到：

* 编造 vs 信息不完整（我的第一判断错了，核对事实才找到真因）
* 守卫死循环（我引入的 bug，测试全绿）
* 口径绕过（数值看着合理，只有对着基线才发现错）
* 语义静默替换（输出完全"正常"，只是答的不是用户问的）

**没有一条能写成布尔断言。** 它们要么需要对着事实核对，要么需要读输出的"感觉"。

结论：以后每加一个功能，都应该配一次"我自己用它"的环节，
而不只是补几条断言。
