# 03 智能体与插件架构

> 本文件讲清一件事：**为什么这个项目从"调用大模型"变成了"智能体"**，
> 以及"一切皆插件"是怎么落地的。

---

## 1. 升级前的真实状态

升级前，项目其实是「LLM 单次调用 + 硬编码流水线」：

```
agent/__init__.py  →  build_graph() 返回 7 个固定节点
                      plan → compile → cache_lookup → guard → execute → cache_store → outcome
contracts/pipeline.py → NodeSpec / Edge / GraphSpec 定义了，但没有执行器读它
registry.py           → 只是内置类的查表，只能注册 7 种固定名字
Tool 契约             → 不存在
```

**缺的不是模型能力，是两样东西：工具、循环。**

`compile` 只会被调用一次；失败了就报错结束。没有"模型看到错误后决定怎么办"的环节。

---

## 2. 分野只有一句话

> **工具执行的结果要回到模型眼前，模型据此决定下一步。**

有了这条，才可能出现：

```
决策：调 sql.execute
观察：[失败] no such column: region
      建议: 字段 region 不存在。真实字段（部分）: 地区、大区…
      ↓ 这一段回到了模型眼前
决策：先调 schema.describe 确认字段
决策：用正确字段重跑 → [成功]
决策：final
```

升级前这条链路不存在——失败信息只用来给用户报错，不会变成模型的下一步输入。

---

## 3. 核心契约

| 契约 | 文件 | 作用 |
|---|---|---|
| `Tool` / `ToolSpec` | `contracts/tool.py` | 工具的声明与执行；`ToolSpec` 同时是给模型看的说明书 |
| `ToolResult` | `contracts/tool.py` | 结果 + **可行动的失败信息**（hint / candidates） |
| `ToolContext` | `contracts/tool.py` | **能力的显式载体**；工具只能拿到被授予的资源 |
| `Capability` | `contracts/tool.py` | 13 项能力清单；未声明即不授予 |
| `Turn` / `SessionState` | `contracts/session.py` | 多轮上下文与回合制澄清 |
| `AgentRuntime` | `agent/runtime.py` | 循环、观测回灌、防打转、硬约束 |

### 三条实现纪律

1. **工具不抛异常**：失败返回 `ToolResult(ok=False, hint=...)`。
   异常会打断循环、丢失上下文，而这正是 agent 最需要的东西。
2. **失败信息必须可行动**：不只说"字段不存在"，还要给候选。
   这是自我纠正的前提。
3. **依赖来自 `ToolContext`**：不 import 核心私有模块，不摸全局。

## 4. agent 循环

```
for step in range(max_steps):
    decision = model.decide(历史 + 可用工具)        # 每步只决定一件事
    if decision.kind == "clarify":  → 结束本轮，等用户回答
    if decision.kind == "final":    → 硬约束校验后结束
    result = tools[decision.tool].run(args, ctx)
    历史.append(观察)                                # ★ 回灌
```

### 两道防线（针对实测暴露的真实故障）

**防线一：没查过就不许答**

实测中模型会"说明口径 / 列出可用指标"来敷衍，甚至编出带 `—` 的表格。
这不是能力问题而是行为问题，**光靠 Prompt 约束不够**，运行时必须顶回去：

```
if 有查询工具 and 一次都没试过 and 不像"确实无法查询":
    回灌"你还没有执行任何查询就给出了回答"
    continue
```

**防线二：过程叙述不算回答**

模型会把"我先查询各渠道的核心指标数据。"写成 `kind="final"`。
这种回答对用户毫无价值，还会掩盖"其实没查"的事实。同样在运行时识别并顶回。

### 成本保护

| 机制 | 作用 |
|---|---|
| `max_steps` | 步数上限 |
| `max_repeat` | 同一工具+同参数重复超过阈值视为打转，强制停止 |

没有这两条的 agent 循环，在模型卡住时会烧钱烧到天荒地老。

## 5. 澄清：为什么选回合制

`clarify.ask` 会打破"一问一答"的同步模型。两种实现：

| 方案 | 机制 | 代价 |
|---|---|---|
| 真暂停 | 挂起运行时、持久化中间状态、回答后从断点恢复 | 需要可恢复状态机 |
| **回合制**（采用） | 立即返回 `status="need_clarification"`，用户回答作为**下一回合**携带上下文重开 | 需会话持久化 |

选回合制的理由：
- 无需可恢复状态机，实现可靠得多
- 天然支持"用户改主意、补充信息、换个说法"
- 人跟人对话本来就是回合制的

### 会话里必须保留的两样东西

1. **时间锚点（`now`）**
   否则用户回答"本月"后，「本月」会漂移到真实今天——同一会话里同一个词
   指了两个月，结果就错了。
2. **工具调用轨迹**
   靠它回答"它为什么这么答"，也是排查的唯一依据。

会话落 SQLite（schema v4），跨请求可恢复。

## 6. 一切皆插件

### 插件目录

```
plugins/<name>/
  plugin.toml     # 声明：name / version / requires（能力）/ tools
  plugin.py       # 必须定义 register() -> list[Tool]
```

### 三档自定义能力

| 档 | 内容 | 需要写代码 | 风险 |
|---|---|---|---|
| 声明式 | Prompt、模型绑定、参数、显式 DAG 连线 | ❌ | 无 |
| 工具 | 注册新 Tool（如 `chart.render`、`anomaly.detect`） | ✅ | 中，走能力白名单 |
| 提供者 | 新数据源适配器、向量库、LLM、规划器 | ✅ | 低，走既有 Protocol |

### 隔离靠什么落地

**插件只能 import `nl2sql.plugins`**（稳定接口），不得碰核心内部。
这条由 `scripts/check_layers.py` 强制，规则名 `PLUGIN_IMPORT`。

为什么这条必须有：若能 import 核心内部任意模块，插件就能绕过能力检查
直接拿适配器，白名单与沙箱全部形同虚设。

### 能力必须显式声明

```toml
[plugin]
requires = ["semantic.read", "source.read"]
```

加载时做**双重校验**：
1. 插件必须在 `plugin.toml` 声明能力，否则拒绝加载
2. 每个工具声明的 `requires` 必须被插件声明覆盖，否则拒绝注册
3. 核心还可以**收回**：只授予配置里也允许的能力

未授予能力的工具**不会被注册**——它的说明也就不会进入模型的工具清单，
模型不会去调一个它看不见的工具。

### 实测：以插件作者的身份写一遍

"可插拔"是个很容易自说自话的声明。验证它的唯一办法是**换个身份**：
不看核心代码，只按文档写一个真插件，看它能不能落地。
脚本 `scripts/plugin_dev_trial.py` 就是这么做的（新增插件 `plugins/trend`，
贡献工具 `trend.compare_periods`，声明 `requires = ["source.read"]`）。

| 试炼 | 结果 |
|---|---|
| 1) 只按文档写 → 能否装载 | 零错误装载；能力按声明授予 |
| 2) 工具单独调用是否正确 | 无分组环比 2024-05 = 210179.88 → 2024-06 = 171907.99，变化率 -0.1821；分组变体 5 组 |
| 3) 默认是否加载外部插件 | `enabled_plugins = ()` → 加载 **0** 个；内置 9 个工具不受影响；写 `["*"]` 才全加载（2 个） |
| 4) 按白名单显式启用 | 只加载 `trend`，工具集 9 → 10；`demo` 被白名单排除 |
| 5) 坏插件是否拖垮系统 | 引擎 0.3s 正常起来；`crash`/`badspec`/`overreach` 被记录不吞掉 |
| 6) agent 是否真的用上新工具 | 真实模型（DeepSeek）`status=ok` 9.4s，工具链 `['trend.compare_periods']` |

第 6 项是最关键的一条：模型面对"6月的实收金额比5月增长了吗？增长了多少？"
**自己选中了刚写的新工具**，没有走内置的 `nl2sql.solve`。回答：

> 没有增长，反而下降了。5月 210,179.88 元 → 6月 171,907.99 元，
> 变化量 -38,271.89 元，变化率 -18.21%。（口径：已支付订单，金额扣除优惠）

这说明插件不是"注册进表里但没人调"的装饰：注册 → 进模型工具清单 → 被自主选中
→ 返回的数字正确，整条链是通的。

### 作者视角暴露的四个真问题（都已修）

1. **聚合函数不能套在 CASE 里**。`CASE WHEN ... THEN SUM(x) END` 直接报
   `misuse of aggregate function SUM()`。改成行级表达式 + 外层 `SUM(CASE ...)`。
   这是插件作者的 SQL 水平问题，但**文档没提醒**——插件作者要自己写 SQL，
   文档得把这个坑写出来。
2. **没有分组时也发 `GROUP BY`**。静默给出错误粒度。插件自己的 bug，但它说明
   "工具的输出对不对"最终仍要靠人验证——运行时只能保证它不崩、不越权。
3. **错误提示不够可行动**。早期非法输入只回一句"参数不对"，作者/用户都不知道
   该传什么。现在统一给"错在哪 + 正确格式 + 候选值"（见上表第 2 行）。
4. **界面里"未启用"的原因会说谎**。插件在白名单里但加载失败时，旧逻辑仍显示
   "不在白名单中"，用户会点一个永远没反应的启用按钮。现在区分
   「没在白名单」与「在白名单里但加载失败」，后者明确指向加载错误并要求重启。

### 一条不能含糊的边界

插件能做的**上限**是"贡献工具"。它拿不到审计豁免、绕不过能力白名单、
也不能在运行期替换自己的代码（改 `plugin.py` 必须重启进程——Python 卸载
已导入模块不可靠，个人工具不值得冒这个险）。

### 一个明确的禁区

**不提供"在进程内执行用户任意代码"的能力。**

允许 `eval`/`exec` 用户代码等于取消所有沙箱：只读守门、能力白名单、审计
会同时失效。要自定义逻辑，走**工具注册 + 能力白名单**。

## 7. 内置工具集（agent 的能力半径）

| 工具 | 作用 | 需要能力 |
|---|---|---|
| `semantic.list_metrics` | 探索：有哪些指标可回答这个问题 | `semantic.read` |
| `semantic.describe` | 探索：某指标的准确口径 | `semantic.read` |
| `schema.describe` | 探索：表结构、字段、**取值域采样** | `source.read` |
| `knowledge.search` | 探索：知识库里有没有相关口径/示例 | `knowledge.read` |
| `sql.plan` | 问题 → 逻辑计划 | `semantic.read` |
| `sql.compile` | 计划 → 方言 SQL | `semantic.read` |
| `sql.execute` | 执行（**内部仍走 guard**） | `source.read` |
| `nl2sql.solve` | 一步到位（原线性流水线整体包装） | `semantic.read` `source.read` |
| `clarify.ask` | 向用户追问（回合制） | `clarify.ask` |

`schema.describe(with_values=true)` 是纠错的关键能力：
模型常猜错取值（写 `'paid'` 而库里是 `'已支付'`），采样一下就知道。

`nl2sql.solve` 的意义是**迁移策略**：旧能力不丢，只是从"唯一路径"
变成"其中一个选项"。agent 可以用它一把梭，也可以在它失败后改走探索路径。

## 8. 实测结果（真实模型 DeepSeek）

### 机制层（脚本化模型，可断言因果）

T1–T6 全通过，重点验证：
- 失败后**换参数重试**（不是盲重试）
- 第 2 步的 Prompt 里**确实含**第 1 步的失败信息与候选（观测回灌）
- 打转被检测、步数上限生效、工具异常被收敛
- 澄清后**立即停止**（不再调用模型）
- 第二回合的 Prompt 里含第一回合的问题

### 真实模型（T7）

```
[1] 清晰问题：3/3 都真的查到了数据
    A1  6.8s  2 步  tools=['nl2sql.solve']  → 99,998.5 元 ✓
    B1  2.8s  2 步  tools=['nl2sql.solve']  → 5 个渠道全表 ✓
    C2  2.6s  2 步  tools=['nl2sql.solve']  → 6 个月 ✓
[2] 缺信息问题：
    「销售额是多少？」
      → status=need_clarification
         "请问您要查询哪个时间范围的销售额？以及按哪个口径统计？"
      → 用户答「本月」→ status=ok → 171,907.99 元 ✓
[3] 轨迹：会话持久化，记录了工具调用与参数
[4] 开放问题「这个库里有哪几张表？」
      → 主动调用 schema.describe 后作答（而非凭空回答）
```

**关键证据**：`answer_contains` 断言答案里含基线中的具体数值。
编造的答案不会命中这些数字——所以这能证明它真的查了。

## 10. agent 的散文答案与结构化结果表

### 问题

agent 的最终回答是**散文**（"实收金额为 99,998.5 元"），但界面需要**结果表**
才能排序、过滤、导出。散文里有数字却没有结构，前端无法还原成表。

### 解法：保留数据，不解析散文

结构化数据**本来就在工具返回值里**，只是之前没往下传：

```
ToolResult.data = {"columns": [...], "rows": [...], "sql": "..."}
        ↓ 之前只用来设了个"查过了"的标志
        ↓ 现在提升为 QueryOutcome.result
QueryOutcome.result = QueryResult(columns, rows, row_count, truncated, sql)
```

**刻意不去解析散文还原表格**——那既不可靠也没必要。

### 两个实现细节

**保留"最丰富"的结果，而不是最后一份**

agent 多步时常先小查一下再正式查。若一律用最后一份，可能把中间用于探路的
空结果当成最终结果给用户看。判据：行数多者优先，行数相同则列数多者优先。

**给模型看的观察 vs 给界面用的结构，分开产出**

| 用途 | 函数 | 特点 |
|---|---|---|
| 喂给模型的观察 | `_compact` | 截断成 8 行预览、紧凑，控制上下文成本 |
| 给界面的结果 | `_to_query_result` | 完整、可排序、带 SQL |

两者从同一份工具结果出发，目的不同，所以不共用实现。

### 界面上两者的关系

```
┌─ 结论（agent 的散文，含真实数字）────────────────┐
│ 2024年上半年各渠道实收金额与有效订单数如下：      │
│ | 销售渠道 | 实收金额 | 有效订单数 |             │
│ | 淘宝     | 216,339.57 | 112 |                 │
└──────────────────────────────────────────────────┘
┌─ SQL（可编辑重跑）───────────────────────────────┐
┌─ 结果表（可排序、过滤、导出 CSV）─────────────────┐
│ 销售渠道 | 有效订单数 | 实收金额                  │
│ 线下门店 | 149       | 182,883.73                │
└──────────────────────────────────────────────────┘
```

结论给判断，表格给明细，SQL 给依据。三者互补而非重复。

### 一个判分上的注意

结果表的**列名不做精确比对**：那是模型生成的别名，
"销售渠道" vs "渠道" 措辞不同不影响正确性。
同样的规则也写在 `golden_set/README.md` 里。
校验的是**列数**与**值**（`rows_match`，行序与列序无关）。

## 11. 会话在界面上的落地

agent 的澄清是多轮的，界面上必须：

| 界面行为 | 原因 |
|---|---|
| 记住 `session_id` 并在下一轮带上 | 否则上下文断，用户答完"本月"它还是不知道在答什么 |
| 追问的**可选项做成可点按钮** | 用户不必打字，点一下就是回答 |
| 追问用 **warn（黄）而不是 bad（红）** | 它是正常交互，不是错误；红色会让用户以为出问题了 |
| 提供「新会话」按钮 | 旧上下文会干扰全新问题，用户需要能主动切断 |
| 顶部显示会话标识（截断显示） | 让用户知道"当前在同一个会话里" |

## 12. 已知边界

| 项 | 状态 |
|---|---|
| agent 模式默认关闭 | 默认仍是 `llm`（单次规划）。agent 多步更慢更贵，应由用户按需开启 |
| 结果表依赖工具产出 | 只有返回 `columns/rows` 的工具才会产生结果表；纯文本工具没有 |
| 前端未接插件管理 | 插件目前靠文件系统，没有界面 |
| 向量检索 | 默认 `HashEmbedder` 是占位实现，非语义向量 |
| 写操作 | 能力清单里有 `source.write`，但**没有任何工具或适配器实现它**——沙箱与审批流程未设计 |

## 14. 容错与上下文预算（2026-10，借 langchain 思路）

真模型和真数据库每天都在抖动。这一节记录 agent 的"坏天气"行为，
来源是读 langchain 官方实现（`langchain_v1/langchain/agents/middleware/`
下的 `_retry.py` / `tool_retry.py` / `model_retry.py` / `summarization.py`）
后落地的三个机制——**只借策略，不搬框架**。

### 14.1 为什么不做 middleware 管线

langchain 的 `create_agent` 把一切挂成 middleware（`before_model` /
`wrap_tool_call` 等钩子），好处是可组合、可插拔；代价是多一层"钩子顺序"
的隐式语义。本项目的 agent 是**显式状态机**（`machine.py` 的
decide/review/act/finish）+ 两个可互换的执行器，护栏位置本来就是一目了然的
`review`。引入 middleware 会为了三个策略加一层适配，收益为负。
所以只把策略搬进两个小模块，由状态机直接调用：

| 文件 | 职责 |
|---|---|
| `nl2sql/agent/resilience.py` | `RetryPolicy`（退避/抖动/上限）+ `retry_call` + 两个分类器 |
| `nl2sql/agent/context.py` | Prompt 历史与会话渲染的预算压缩 |

### 14.2 三个机制

**① 模型调用重试（`_ask_model`）**

- 只对**瞬态**故障重试：超时、连接重置、限流（429）、5xx。
  认证失败（401）、参数错（400）、内容安全这类重试没有意义，**一次就失败**，
  错误原样告诉用户。
- 默认 `max_retries=2`、`initial_delay=0.5s`、`×2` 退避、`8s` 封顶、±25% 抖动。
- 不用 openai SDK 自带的 `retries` 做主力：它是黑盒——重试了没有、为什么，
  trace 和界面里都看不见。SDK 的 retries 保留在最底层兜底，两层不互相放大。
- 每次重试都留痕：`trace["llm_retries"]`、`notes`、SSE 事件 `model_retry`。

**② 决策修复（`_repair_hint`）**

真模型最常见的失败不是网络，而是**输出不像话**：

- `finish_reason == "length"`：推理写太长把 JSON 截断了；
- 空回复；或看起来是 JSON、解析出来却是残缺的 final。

这时"原样重试"没用，要把**错在哪、要怎么改**写进下一轮 user 消息再问一次
（默认 `llm_repair_attempts=1`）。**纯文本回答刻意不修**：
`parse_decision` 本来就容忍它当 final（用户至少能看到模型说了什么），
强行纠正可能把一次能用的回答弄没了。留痕：`trace["llm_repairs"]`、
事件 `model_repair`。

**③ 工具调用重试（`invoke`）**

- **只对只读工具**：写工具可能不幂等，重试一次就是多写一次；
- **只对瞬态异常**：`database is locked`、连接断开、deadlock；
- SQL 写错、字段不存在这类**确定性失败绝不重试**——错误原样回灌给模型，
  让它改 SQL，比"把同一个坏 SQL 再跑一遍"有用得多；
- 默认 `tool_max_retries=1`（只给一次机会），退避从 0.2s 起；
- 重试过的工具调用在 `ToolContext.trace` 的 note 里带 `retries` 字段，
  否则用户看到"这次查询慢"不知道慢在哪。

### 14.3 上下文预算：不引入摘要模型

跨轮会话里持久化的工具输出是**完整**的（界面要能追溯"为什么给这个答案"），
但喂给模型只需要最近几条。做法是**按字符预算压缩**（`context.py`）：

| 函数 | 用途 | 默认预算 |
|---|---|---|
| `compress_prompt_history` | 决策 Prompt 里的本轮历史 | 14000 字符；最近 3 条观察保留全文，更早压成一句 |
| `compress_session_context` | 跨轮会话渲染 | 4000 字符；每行截断到 600，超预算时保留最近的行 |

为什么不学 langchain 的 `SummarizationMiddleware` 用摘要模型：
多一次模型调用、引入非确定性、还多一份要维护的 Prompt；而我们的历史是
**结构化的**（"观察: 工具结果"），按预算裁旧观察既便宜又可复现。
压缩只发生在**渲染层**——`state["history"]` 与 session 里的完整记录不受影响，
所以追溯能力和 Prompt 成本可以分别优化。
