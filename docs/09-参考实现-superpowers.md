# 09 参考实现：Superpowers（技能型智能体的一个成熟范本）

> 素材：`superpowers-main/`（obra/superpowers，MIT，16 个 harness 适配）。
> 用途：作为 `docs/08-技能设计草案.md` 的**对照实现**——
> 那份草案还停在"待拍板"，这份材料里有几处能直接把它问对。
> 本文只记**可核对的结论**，每条都标了出处路径。

---

## 1. 它是什么，不是什么

**是**：一套给**已有编码 agent** 用的技能库 + 开发方法论。
仓库里只有技能（Markdown）、钩子（shell）、各家 harness 的清单（JSON）、
文档与测试。**没有 agent 运行时、没有工具实现、没有模型调用。**

**不是**："agent 智能体搭建范本"意义上的框架或脚手架。
它自己不起 agent，它是挂到别人 agent 上的内容层。

所以拿它当范本时，**能借的是内容层的架构**（技能格式、发现、注入、
可移植性、测试方法），不能借它的运行时——我们的运行时
（`nl2sql/agent/`：工具循环、能力白名单、守门、`max_steps`）是自己的。

规模供参照：238 个文件 / 2.0 MB；15 份技能，最大的一份
`subagent-driven-development/SKILL.md` 32 KB，最小 3 KB；
`RELEASE-NOTES.md` 109 KB。

## 2. 它的架构：三件套 + 两条规则

出处：`docs/porting-to-a-new-harness.md` 第 31–77 行。

| 组件 | 谁负责 | 我们的对应物 |
|---|---|---|
| **Skills**（`skills/`，逐字共享） | 全部逻辑与知识，写**动作**不写工具名 | 我们**还没有**（`docs/08` 要补的） |
| **Tool mapping**（`skills/using-superpowers/references/<harness>-tools.md`） | 把动作词翻成该 harness 的真实工具名 | 没有 |
| **Bootstrap**（每个 harness 一个注入器） | 会话开始时把 `using-superpowers/SKILL.md` **整份注入** | 我们的 `_load_decision_prompt()`（只有一个槽） |

两条规则（原文第 57–77 行）：

1. **技能说动作，不说工具。** 技能正文只写"invoke a skill""read a file"
   "dispatch a subagent"，从不出现具体工具名；适配层负责翻译。
   **禁止**为了适配某个 harness 去改技能正文——
   他们把技能正文当"经过调优的、塑造行为的代码"。
2. **一切通过 harness 自己的安装机制交付，绝不改用户的文件。**
   bootstrap / 技能 / 工具映射都得随"装的东西"一起进去
   （plugin、extension、marketplace 条目）；
   不许伸手去改用户 home 下的 `settings.json`、`AGENTS.md`、`~/.bashrc`。
   如果安装机制装不下 bootstrap，那是**要明说的限制**，不是改用户配置的理由。

## 3. 最硬的一条：引导必须**强制注入**，不能靠"可发现"

`porting-to-a-new-harness.md` 第 86–106 行把它列为**唯一的硬性要求**，
第 49–55 行说得更直白：

> 会话开始时把整份 `using-superpowers/SKILL.md` 注入上下文，
> 用 `<EXTREMELY_IMPORTANT>` 包起来，附上工具映射。
> **bootstrap 就是整个集成的全部。没有它，技能文件是惰性的——
> 躺在磁盘上，永远不会被调用。**

并且明确否掉了几种做法（`AGENTS.md`）：手工复制技能文件、
用 `npx skills` 之类的运行期垫片、需要用户按会话开启的方式，
**都不算真集成**。验收测试是一句话：干净会话里发
`Let's make a react todo list`，必须**在写任何代码之前**自动触发
`brainstorming` 技能。

机制上（`hooks/hooks.json` + `hooks/session-start`）：
`SessionStart` 钩子匹配 `startup|clear|compact`，读 SKILL.md 正文、
转义成 JSON、作为 `additional_context` 注入。
**`compact` 也在匹配列表里**——上下文压缩会把 bootstrap 压掉，必须重新注入。
（他们自己记录了反例：Hermes 没有 post-compaction 钩子，
长会话压过头之后就失效了。）

### 这对 `docs/08` 的直接后果

`docs/08` 第 6 节我推荐 **A（工具式按需加载）**，并诚实地写了它的风险：

> 一个诚实的取舍：A 依赖模型主动调用。如果模型不调，技能就白写了。

这份参考实现说的正是：**这个风险不能靠"把 description 写好"来缓解，
要靠强制注入一个 bootstrap 来消除**。它的做法是折中而清晰的：

* **强制注入**的只有**一份很小的引导**（3.2 KB）——它的唯一职责是
  "你必须先检查有没有适用技能，以及怎么加载"；
* **其余技能**仍然按需加载（渐进披露）。

也就是 **A + 强制引导**，不是纯 A。这是 `docs/08` 第 6 节要改的第一处。

## 4. 第二条可迁移的：技能说"动作"，不说"工具"

这条对我们**比对一般项目更重要**，因为我们的工具会**消失**：

`docs/04` / `nl2sql/config.py` 里，能力没授予的工具**根本不注册**，
它的说明也不会进模型清单。如果技能正文写死"调用 `sql.execute`"，
在没授予 `source.read` 的场景下这份技能就是**错的**——
它会教模型去调一个不存在的工具。

参考实现的做法正是为此设计的（`porting-to-a-new-harness.md` 第 112–122 行）：

| 能力 | 缺失时的处置 |
|---|---|
| 技能发现与调用 | 没原生技能工具就**直接读 `SKILL.md`** |
| 子 agent 派发 | **可降级**：技能里已经写好"没有这个能力就在当前会话里做，或如实报告缺什么"，**绝不**让模型凭空发明一个调用 |
| 待办跟踪 | 可降级：退回计划文件 |

原文一句原则："**可降级**意味着技能里已经写了缺工具时的兜底措辞；
你的工作是工具存在时指向真工具、不存在时沿用那段兜底。"

对我们的具体含义：

* 技能正文写"查一下这个指标的口径"，**不写** `semantic.describe`
* 每个壳（`apps/web` / `apps/sdk` / `apps/internal`）提供自己的
  **动作 → 工具**映射，而不是让技能去适配壳
* 工具因能力未授予而不在时，技能要能**如实说缺什么**，而不是照旧指示

`codex-tools.md` 里还有一句很值得抄的态度：
"**当实际工具清单和这张表冲突时，以实际工具清单为准**"——
映射文件是提示，运行时才是真相。

## 5. `writing-skills`：技能不是散文，是用 TDD 写出来的代码

`skills/writing-skills/SKILL.md`（26 KB）是这个仓库里最有方法论价值的一份。
三条与我们直接相关：

### 5.1 `description` 只写**何时用**，绝不概括流程

原文（第 150–158 行）带实测依据：

> **描述里概括了流程，agent 就可能照着描述做而不去读技能正文。**
> 一条写着"code review between tasks"的描述，让 agent 只做**一次** review，
> 而技能里的流程图明明写着两次（先规范符合性、再代码质量）。
> 改成只写触发条件后，agent 才正确读了流程图。

配套硬约束：frontmatter 总长 ≤ 1024 字符，`description` 建议 < 500；
`name` 只用字母数字连字符；描述用第三人称、以"Use when…"开头。

**`docs/08` 第 5 节我给的示例描述是错的**：

```yaml
# ❌ 我写的（末尾那句概括了产出，会诱导模型照描述做而不读正文）
description: 用户要把两个时间段的同一指标并排比较时使用（…）。产出多列宽表。

# ✅ 按他们的标准
description: 用户把两个时间段并排提问时使用（"本月和上月""同比""环比"）
```

### 5.2 技能的创建就是 TDD，铁律是"没有失败的测试就不写技能"

> **NO SKILL WITHOUT A FAILING TEST FIRST**（第 376–395 行）
> 基线（不给技能，看 agent 怎么错）→ 写技能 → 再看 → 补漏洞。
> "如果你没亲眼看过 agent 在没有这个技能时失败，你就不知道技能教对了没有。"

而且按技能类型分测试法（第 397–445 行）：
纪律类测**压力场景下的服从**、技术类测**能否迁移到新场景**、
模式类测**识别与反例**、参考类测**检索与套用**。

### 5.3 "Match the Form to the Failure"：形式要匹配失败类型

这是全篇最锋利的一节（第 461–477 行），带 head-to-head 措辞实验：

| 基线失败 | 对的形式 | 错的形式 |
|---|---|---|
| 压力下**违反规则**（知道该做却不做） | 禁令 + 合理化对照表 + 红旗清单 | 软性建议（"prefer…""consider…"） |
| **照做了，但产出形状不对** | **正面配方 / 契约**：直接说产出**是什么**、有哪几部分、按什么顺序 | **禁令清单**（"不要说…""永远别…"） |
| 产出里**漏了必需项** | 结构化：在模板里设**必填槽位** | 模板旁边的散文提醒 |
| 行为应当**依条件而定** | 以**可观测谓词**为键的条件式 | 无条件规则 + 豁免条款 |

并给了两条可操作的禁令：

* **不许加含糊从句**："不要 X，除非它重要"会把谈判重新打开——
  实验里给一个已经赢了的配方追加一句含糊从句，效果从稳定退化到噪声。
* **豁免条款不成立**："这个限制不适用于代码块"仍然会抑制代码块。
  要豁免就**重构结构**让规则够不着，而不是加例外。

## 6. 拿这张表审我们自己的 Prompt（具体发现）

`nl2sql/agent/runtime.py` 的决策 Prompt 里有多条**禁令**。按上表分类：

| 我们的原文 | 失败类型 | 形式对不对 |
|---|---|---|
| "业务指标必须走语义层，不要自己拼 SQL"（第 107 行） | 纪律（知道该做却抄近路） | ✅ 禁令正确 |
| "不要反复探查"（第 123 行） | 纪律 | ✅ 正确 |
| "禁止在未取得真实数字的情况下'说明口径''列出可用指标'或给出表格"（第 82 行） | **形状**（照做了但产出形状错：给了解说而非数字） | ⚠️ **可疑**——形状问题用禁令，按他们的实测可能反而更多 |

第三条是**具体、可核对**的一处：我们在 `docs/03` 第 4 节记录过这类真实故障
（agent 用"说明口径"代替回答、用"我可以继续"代替回答），
运行时的处置是加了检测器（`_is_narration` / `_is_deferred_promise` /
`_carries_query_data`）——**机制那一路是对的**。但 Prompt 那一路用的是禁令列表，
而他们实测：形状问题上**配方 > 禁令**，且禁令可能比不加引导还差。

对应的正面配方应该直接写"最终答复**是什么**"：
先给结论数字，再给口径声明，最后给来源——而不是列一串"不要"。
（我们已经有 `{"kind":"final","answer":…}` 这个结构槽，
配方写进去是自然的。）

> ⚠️ **我没有做这项审查的完整版**。上表只是我按他们的分类法抽查决策 Prompt
> 得到的一处；规划器 Prompt、校验器 Prompt、`docs/03` 里那些行为约束都还没过一遍。
> 这件事本身值得单列成一项任务。

## 7. 测试分层：他们怎么分开"集成"与"行为"

`tests/` 的目录结构本身就是一份答案：

| 层 | 例子 | 测什么 |
|---|---|---|
| **各 harness 的集成测试** | `tests/hooks/test-session-start.sh`、`tests/opencode/test-session-bootstrap.sh`、`tests/opencode/test-bootstrap-caching.mjs`、`tests/pi/test-pi-extension.mjs`、`tests/hermes/test_bootstrap.py` | 清单合法、插件能加载、**bootstrap 真的被注入**、注入有缓存 |
| **行为触发场景** | `tests/explicit-skill-requests/prompts/*.txt`（9 份）——`please-use-brainstorming.txt`、`skip-formalities.txt`、`i-know-what-sdd-means.txt`、`action-oriented.txt`… | 技能**是否被触发**；文件名本身就是"合理化场景" |
| **组件测试** | `tests/brainstorm-server/*.test.js`（含 ws 协议、生命周期、Windows 生命周期） | 附带脚本/服务的正确性 |
| **工具自身** | `tests/version-bump/test-bump-version.sh`、`tests/shell-lint/test-lint-shell.sh` | **连版本同步脚本和 shell lint 都有自己的测试** |

而**技能行为评测**（技能有没有塑造出正确行为）**不在这个仓库**——
放在独立仓库 `superpowers-evals`，克隆到 `evals/`，用真实 coding agent CLI 跑
"压力场景 + 验收标准 + 确定性后置检查"。

### 这对 `docs/08` 第 11 节的直接后果

我在那里写了"**测不了的（如实说）：技能是否真的让答案变好**"。
这个判断**过于悲观**——他们有可运行的做法：**基线对照**。
而且这正是我们自己已经在用的方法（`docs/02` 第 19 节：
"对照实验：同一条链路跑两次（知识库空 vs 有种子），差值才是真实贡献"）。

正确的说法是：**可测，但要换一套场景集**——不是 SQL 对错，
而是**决策对错**（该追问还是该直接查、该披露假设还是静默替换）。
代价是要新建一个压力场景集，我们目前没有。这是"还没做"，不是"做不到"。

同时他们的分层也提示我们：**集成测试**（技能被发现了、被注入了、正文完整）
和**行为测试**（技能真的改变了行为）应该分开，前者进 `tests/`，
后者需要另一套机制。

## 8. 明确**不该**抄的部分

诚实划界。他们的核心命题是"**强制流程**"——用户一问就先把
brainstorming 拽出来，把需求问清楚再写代码。这套东西成立的前提是
**过程正确性就是产出质量**。我们不是：

| | Superpowers | 我们 |
|---|---|---|
| 用户 | 用编码 agent 的开发者 | 问数据问题的个人工作者 |
| 失败代价 | 流程没走 → 代码质量差、返工 | **数字错 → 直接误导决策** |
| 所以优化 | 过程服从（mandatory workflows, not suggestions） | **口径正确性** |
| 我们的技能该讲 | — | "这个口径怎么算""该不该追问""没数据时怎么说" |

具体的：

1. **不要抄"MANDATORY / 不许讨价还价"的语调。** 那套语气是为
   "agent 在压力下偷懒"设计的；我们的失败模式是**静默替换口径**、
   **拿不到数就编**，对策是机制（守门、检测器）加**清楚的披露要求**，
   不是把用户按在流程上。
2. **不要抄 `subagent-driven-development` / worktrees / TDD 流程。**
   那是编码 agent 的工作流，与"自然语言转 SQL"无关。
3. **bootstrap 的成本模型不同。** 我们 agent 模式实测 1–2 步工具调用、
   1.1–7.1 秒（`docs/03` 第 8 节），`max_steps=8`。
   强制"先检查技能"会**每轮多吃一步**。3 KB 引导本身进 system prompt
   是一次性成本（可接受），但"必须检查"这一步要不要加、加在哪，
   得按我们的延迟预算算，不能照搬。
4. **他们的 `description` 只写触发条件、绝不概括流程**——这条要抄，
   但要注意与我们的**同义词匹配**机制共存：
   规则规划器靠 `synonyms` 做确定性匹配，`description` 是给模型看的。
   两者都要有，且不能互相冒充（`docs/06` 里 dbt 的同义词就踩过"两处真相"的坑）。

## 9. 顺带值得记的一条维护经验

`.version-bump.json` 列了 **12 个文件/字段**要同步版本号
（`package.json`、7 个 harness 的 `plugin.json`、2 个 marketplace、
`gemini-extension.json`），配 `scripts/bump-version.sh`，
而**这个脚本自己也有测试**（`tests/version-bump/test-bump-version.sh`）。

这是"一套内容 N 个壳"的**维护税**，而且他们选择：
**用脚本同步 + 给脚本写测试**，而不是靠人记得。

我们的版本号现在还散在 `nl2sql/__init__.py`、`pyproject.toml`、
`apps/web/frontend/package.json`，将来还有壳②壳③的清单。
现在只有 3 处，手工还好；到 6 处就该照这个做法办。

## 10. 结论：对 `docs/08` 的三处修正

| # | `docs/08` 原稿 | 改成 | 依据 |
|---|---|---|---|
| 1 | §6 推荐纯 A（工具式按需加载），风险"模型不调就白写" | **A + 强制注入一份小引导**（bootstrap）；纯按需在这份参考实现里被明确判定为失效 | 第 3 节 |
| 2 | §5 格式契约只有 frontmatter 字段；示例描述概括了产出 | 新增**"技能说动作不说工具"**为硬规则；新增**降级措辞**要求；修示例描述为"只写触发条件" | 第 4、5.1 节 |
| 3 | §11 "技能效果测不了" | **可测**：用我们已有的对照实验法，但要新建一套**决策场景集**；集成测试与行为测试分层 | 第 7 节 |

另外新增一项独立任务（不在 `docs/08` 范围，但由第 6 节引出）：
**按"形式匹配失败类型"审一遍我们所有的 Prompt**
（决策 / 规划 / 校验三处，以及 `docs/03` 里的行为约束）。
