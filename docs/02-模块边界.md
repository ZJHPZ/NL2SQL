# 02 模块边界

每个模块一节，格式固定为：**职责 / 明确不做 / 公开接口 / 依赖 / 关键取舍**。
字段名与签名以 `nl2sql/contracts/` 下的实际代码为准，本文只讲边界与理由。

---

## 1. contracts —— 契约层（最高稳定度）

| 项 | 内容 |
|---|---|
| **职责** | 定义全部接口与数据模型；承载跨模块共享的类型 |
| **明确不做** | 任何逻辑实现；任何第三方依赖 |
| **文件** | `source.py` `semantic.py` `knowledge.py` `storage.py` `pipeline.py` |
| **依赖** | 仅标准库（contracts 内部允许互相引用——它本就是一个整体） |

契约层的稳定度决定了后期重构成本，因此这里刻意**只在确有第二种实现时才抽象**。

### 关键取舍

**① `LogicalPlan` 必须确定性，指纹不含 `notes`**

```python
def normalized(self) -> dict:   # 排序后的字典，字段顺序稳定
def fingerprint(self) -> str:   # sha256 前 32 位
```

理由：指纹是结果缓存的唯一键。若把"未验证口径"这类提示文案算进指纹，
同一计划会因提示文字不同而缓存分裂。**提示属于呈现，不属于计划。**

**② 相对时间必须显式锚定**

```python
def resolve(self, question, *, source_id, now: str | None = None) -> LogicalPlan
```

理由：`本月` 若读系统时钟，同一问题在不同日期得到不同结果——
评测不可复现、缓存语义错乱。`now` 由调用方（壳/评测器）传入。

**③ `QueryOutcome` 把错误当成正常返回值**

失败不抛异常，而是带 `status` / `message` / `suggestions` / `candidates` /
`applied_filters` 返回。理由见第 10 节。

**④ `SourceCapabilities` 驱动降级，而不是 `if dialect == ...`**

新增数据源只改适配器，核心层读能力表决策。

## 2. config —— 配置

| 项 | 内容 |
|---|---|
| **职责** | 配置模型、校验、便捷构造 |
| **明确不做** | 不读环境变量做隐式配置；不存明文密码 |
| **依赖** | contracts |

**关键取舍：不读环境变量。** 否则"同一个 config 行为不同"，测试与排障都会变难。
需要环境变量时，由壳读取后**显式填入**。

**密码不进配置**：只有 `credential_ref`（指向 OS 凭据存储/本地加密库的键）。

---

## 3. registry —— 组件注册表

| 项 | 内容 |
|---|---|
| **职责** | 适配器 / 语义提供者 / 检索器 / DAG 节点 / 向量库 / 向量化器 / 模型 的注册与查找 |
| **明确不做** | 不做实例生命周期管理（只管"名字 → 类/工厂"） |
| **依赖** | contracts, errors |

**关键取舍：注册表是实例，不是模块级全局。**
每个 `NL2SQL` 持有自己的 `Registry`。这样多数据源、测试、多工作区互不污染——
这也直接满足了"核心无全局状态"的硬约束。

**用户自定义组件的入口就在这里**：自定义 Prompt / 换模型 / 自定义节点，
都表现为注册一个具名实现，而不是改引擎代码。

---

## 4. storage —— 持久化

| 项 | 内容 |
|---|---|
| **职责** | 元数据、知识、历史、结果缓存、向量的落盘 |
| **明确不做** | 不含业务判断（例如"哪些知识该召回"是 knowledge 的事） |
| **实现** | `SqliteMetaStore` `SqliteKnowledgeStore` `SqliteResultCache` `MemoryVectorStore` `HashEmbedder` |
| **依赖** | contracts, config |

### 数据表清单

| 表 | 用途 |
|---|---|
| `data_source` | 数据源配置（无明文密码） |
| `snapshot` / `table_meta` / `column_meta` | 元数据快照 |
| `history` | 查询历史（支撑回放与结果复用） |
| `knowledge_entry` / `knowledge_rev` / `knowledge_fts` | 知识条目、全量修订、BM25 索引 |
| `result_cache` | 结果缓存，主键 `(source_id, plan_fingerprint)` |

**关键取舍：**

- **缓存主键含 `source_id`**。个人用户会同时连测试库与生产库，串缓存是灾难。
- **知识修订全量留痕**。`upsert` 先写 `knowledge_rev` 再更新主表；
  `rollback` 从修订恢复并**生成新版本号，不回退版本号**（否则历史会分叉）。
- **默认全 SQLite**。个人场景零配置优先，不引入外部服务。
- `HashEmbedder` 是**免依赖占位实现**（字符 n-gram 哈希），不是语义向量。
  它的价值是让 P0 不阻塞、接口先跑通；真正语义检索换本地模型或远端 API。

---

## 5. sources —— 数据源适配

| 项 | 内容 |
|---|---|
| **职责** | 能力声明、连接、元数据抽取、只读执行、EXPLAIN |
| **明确不做** | 不做安全校验（那是 guard）；不做 SQL 生成（那是 dialect）；不做缓存 |
| **P0 实现** | `SqliteAdapter`（S2）、`MysqlAdapter`（S8） |
| **依赖** | contracts |

**关键取舍：**

- **SQLite 以只读 URI 打开**（`file:...?mode=ro`）：从连接层兜底，不只靠上层校验。
- **方言差异在适配器内部消化**，不外泄为调用方的 `if` 分支。
  生成列、注释、分页语法都属于适配器的事。
- **`introspect()` 可缓存，`execute()` 必须实时**。
- `columns.py` 提供**相似列名候选**：生成的 SQL 引用不存在的列时，
  给候选而不是抛原始错误（见第 10 节）。

---

## 6. dialect —— 方言编译与校验

| 项 | 内容 |
|---|---|
| **职责** | `LogicalPlan` → 方言 SQL；SQL 静态校验 |
| **明确不做** | 不执行、不连接数据库、不做安全策略 |
| **依赖** | contracts, sqlglot（S3 起） |

**关键取舍：不让 LLM 直接写方言 SQL。**

```
LangGraph 管编排（高层决策）  +  sqlglot/SQLAlchemy 管方言（确定性编译）
```

`SqlCompiler` 先用字符串模板 + sqlglot 转译，**不要一上来就写完整 SQL AST 生成器**——
那是过度设计，P0 的方言需求只有 SQLite/MySQL。

`SqlValidator` 检查四项：只读性、引用存在性、强制 LIMIT、方言合法性。

---

## 7. guard —— 执行守门

| 项 | 内容 |
|---|---|
| **职责** | SQL 落地前最后一道确定性校验：只读、禁多语句、强制 LIMIT、超时 |
| **明确不做** | 不做权限模型（个人场景无多租户）；不做 SQL 改写优化 |
| **依赖** | contracts |

**关键取舍：用 AST 判语句类型，不要用正则。**
正则判只读会在注释、字符串字面量、CTE 上翻车——
`SELECT 'DROP TABLE x'` 会被正则误判为写操作，而 `/* */ DROP TABLE` 会被漏判。

**原则：授权与安全由网关确定性校验，绝不交给模型或 Prompt 判断。**

---

## 8. cache —— 结果缓存

| 项 | 内容 |
|---|---|
| **职责** | 逻辑计划指纹 → 结果集的读写 |
| **明确不做** | **不做跨会话语义相似缓存**（已明确去掉） |
| **依赖** | contracts, storage |

**关键取舍：只保留确定性指纹缓存。**

| 层级 | 决策 | 原因 |
|---|---|---|
| 结果缓存（指纹 → 结果） | ✅ 保留 | 个人用户反复问同类问题，命中率高 |
| 跨会话意图缓存（问题 → 计划） | ❌ 去掉 | 判断错了没人发现，会静默返回错误计划 |

失效策略：**TTL + 手动刷新 + 界面明示数据时间**，不做 CDC（太复杂）。
写缓存失败不得影响正常返回（降级为不缓存）。

---

## 9. semantics —— 语义层

| 项 | 内容 |
|---|---|
| **职责** | 加载 dbt `metrics.yml`；问题 → `LogicalPlan` |
| **明确不做** | 不生成 SQL；不连接数据库；不做鉴权 |
| **依赖** | contracts, config |

**关键取舍：**

- **兼容 dbt `metrics.yml`，不自创 DSL。** 生态中已有定义可零迁移加载，
  也避免自创格式被后期推翻。
- **未覆盖时抛 `SemanticResolutionError`**，由上层决定"自由生成并标注未验证口径"，
  而不是硬猜一个指标。
- 语义层由**开发者自己维护**，不做平台化。

**落地情况（S3b）：** 加载器已实现，见 `docs/06-dbt指标加载.md`。

| 文件 | 职责 |
|---|---|
| `dbt_loader.py` | dbt 指标 YAML → `SemanticModel`（**语义层的本体**） |
| `golden_model.py` | 黄金集**参考模型**（评测基准 + 等价性验收的对照物） |
| `golden_plans.py` | 手写逻辑计划（S3 阶段用，现在主要供回归） |

`api.py` 的装配优先级：数据源的 `semantic_path`（dbt 指标文件）> 内置参考模型。
指向不存在的文件**报错**而不是静默退回——静默退化会让用户以为自己的口径生效了。

两个来自 dbt 规范本身的设计约束：

- **过滤必须编译成条件聚合**（`SUM(CASE WHEN c THEN x END)`）而不是 WHERE。
  写成 WHERE 会把分组里其它行一起筛掉：数字看着像对的，口径已经变了。
- **不静默近似不支持的指标类型**。`cumulative` 需要 time spine、
  `conversion` 需要事件配对，语义层没有这两个概念。近似一个累计指标
  会给出错误数字，所以拒绝并说明替代做法。

## 10. knowledge —— 知识库

| 项 | 内容 |
|---|---|
| **职责** | 条目管理（免审+版本+停用）、多路召回、库注释自动生成 |
| **明确不做** | 不做审批流；不做跨租户共享 |
| **依赖** | contracts, storage |

**关键取舍：**

- **免审 ≠ 无版本。** 没有 draft/pending/active 审批流，
  但保留 `enabled` 开关 + 全量修订 + 回滚。出问题时必须能定位到某条知识。
- **测试检索是一等能力。** 没有它，知识库的错误是**静默的**——
  用户永远不知道自己的问题实际召回了什么。
- **自动生成降低上手门槛**：首次连接数据源时从库表注释生成初版条目，
  用户不必面对空白页。且必须幂等：已存在的 key 不覆盖用户改动。
- 四类召回（schema / 业务 / 相似SQL / 纠错）**统一 Retriever 接口**，
  后期换向量库、加图检索、加精排都不动上层。

---

## 11. catalog —— 元数据目录

| 项 | 内容 |
|---|---|
| **职责** | 元数据抽取、快照缓存、渲染 DDL 上下文、快照差异 |
| **明确不做** | 不做语义（业务含义属于 semantics） |
| **依赖** | contracts, storage, sources |

**关键取舍：绝不把整库 DDL 全塞进 prompt。**
`render_ddl(max_tables=...)` 必须有限制，配合检索按需注入。

`diff_snapshots` 用于提示"表结构变了，知识库可能需要更新"——
这是知识库不腐烂的关键机制。

## 12. agent —— 编排

| 项 | 内容 |
|---|---|
| **职责** | LangGraph 管线、节点执行、把失败翻译成可操作结果 |
| **明确不做** | 不做 HTTP；不做 UI 渲染；不持有跨请求状态 |
| **依赖** | 其余全部模块 |

**关键取舍：**

- **`langgraph` 只出现在 `agent/` 里**，核心其他模块不依赖它。
  这样换编排框架的爆炸半径被限制在一个目录内。
- **`cache_lookup` 在 `plan` 之后**：缓存键是逻辑计划指纹，
  问题换个说法只要计划相同就应命中。
- **DAG 引擎通用**：`NodeSpec` 不假定任何 RAG 专用字段。
  P0 只暴露 RAG 节点，但结构上任何组件都能成为节点——
  后期扩展是"加节点"，不是"重写引擎"。
- **`ErrorOutcomeBuilder` 是产品体验核心，不是收尾工作。**

### 错误与边界反馈清单（必须实现）

| 情况 | 必须有 |
|---|---|
| 列名/表名不存在 | `candidates` 给出可用字段候选，**不抛数据库原始错误** |
| 结果为空 | `applied_filters` 回显实际生效的过滤条件 |
| 超时 / 太慢 | `suggestions` 提示加时间范围或维度限制 |
| 结果被截断 | `status="truncated"`，明示"仅显示前 N 行（共 M 行）" |
| 未覆盖口径 | `notes` 加"未验证口径"，**不静默** |
| 被安全拦截 | `status="blocked"` + 命中的规则名 |

## 13. api —— 门面

| 项 | 内容 |
|---|---|
| **职责** | 装配依赖、暴露 `NL2SQL` 类 |
| **明确不做** | 不做业务逻辑；不读全局 |

## 14. 三个壳

| 壳 | 定位 | 一期做到哪 |
|---|---|---|
| `apps/web` | 本地 Web 前后端（首发） | 后端 API + 结果表页面 |
| `apps/sdk` | 对外 Python SDK | 再导出 + 便捷构造，不含逻辑 |
| `apps/internal` | 内部工具外壳 | Web + 定制，复用 `apps/web` |

**壳的三条纪律**

1. 不写业务逻辑，只做参数装配与格式转换
2. 通过显式配置构造核心，不读全局
3. 只依赖核心公开路径，不 import 内部私有模块

## 16. S2 实施记录：两个必须记住的坑

这两个问题的共同点是：**实现时才暴露，且失败是静默的**。写进文档避免重蹈。

### 坑一：SQLite 只读必须显式 `?mode=ro`

```python
# 错误写法：以为 file: 前缀就等于只读
"file:" + path                      # → 实际是 rwc（可读写创建）！

# 正确写法
"file:" + urlencode(path) + "?mode=ro"
```

SQLite 在 URI 未指定 `mode` 参数时默认 `rwc`。**只给 `file:` 前缀不会得到只读连接。**
后果：适配器以可写模式打开生产库，"只读兜底"形同虚设。

**暴露过程**：S2 测试里"写操作应被拒绝"的探针**真的在黄金集数据库里建了一张表**。
是数据库被污染提醒了我，而不是断言失败。

> 教训：安全兜底的测试必须在**副本**上跑。
> 现在 `test_adapter` 用副本，另有 `scripts/check_golden_db.py` 校验基线数据库完整性。

### 坑二：FTS5 的 `unicode61` 不切分中文

```sql
-- 文档正文含"实收金额"，但：
SELECT ... WHERE knowledge_fts MATCH '"金额"'    -- → 0 命中
```

`unicode61` / `porter` 会把一整段连续中文当作**单个 token**。
因此"金额"这类子串永远查不到——**不报错，只是静默召回不到**。

**修复**：入库时把 CJK 连续段预先切成**重叠二元组**并用空格连接
（`"实收金额"` → `"实收 收金 金额"`），查询侧用同一套切分。
逻辑集中在 `storage/text.py`；**入库与查询必须共用同一函数**，
否则索引与查询的 token 对不上，又是静默失效。

**已知取舍**：
- 会产生"收金"这类跨词边界噪声 token（只影响排序权重，不影响命中与否）
- FTS5 不索引纯数字 token（`40` 查不到）；数字通常不是知识条目的检索词

**迁移**：schema 版本升至 v2，迁移时重建 FTS 索引。
FTS 是派生数据，重建不影响 `knowledge_entry` / `knowledge_rev`。

### 附带发现

| 发现 | 处理 |
|---|---|
| `PRAGMA table_info` **不返回生成列** | 改用 `PRAGMA table_xinfo`，并给 `ColumnMeta` 增加 `generated` 字段。否则 `fact_order.amount` 会被漏掉，"列名不存在"会误判并给出错误候选 |
| 执行沙箱拒绝写入 `tempfile.mkdtemp` 创建的目录 | 测试改用确定性路径 + `makedirs`（环境限制，非代码问题）。顺手也让失败残留可被下次运行清理 |

## 17. S3 实施记录：编译器的四个坑

S3 的验收标准是「**用手写 LogicalPlan 跑通黄金集 30 题**」。
过程中暴露的问题几乎全在"编译"这一层，且都属于**能跑但结果错**或**语法边界**类。

### 现状：30 题的计划来源分布

| 来源 | 数量 | 说明 |
|---|---|---|
| 品语义（measures / dimensions / filters） | 21 | 走完整语义层路径 |
| `raw_select` 逃生通道 | 9 | 跨期对比、按天+HAVING、累计、窗口排名、子查询比较 |

**关键观察**：语义层不该为了覆盖率把自己撑成 SQL 生成器。
9 道复杂查询用 `raw_select` 表达，但它们**仍然走 guard / cache / 结果比对**，
所以链路同样被验证过了。这批查询的归宿是 S6 知识库里的 few-shot 示例。

### 坑一：`GROUP BY expr AS alias` 是语法错误

```sql
GROUP BY ch.channel_name AS "渠道"   -- ✗ syntax error near "AS"
GROUP BY ch.channel_name             -- ✓
```

GROUP BY 必须用**不带别名**的表达式。踩坑点是：`select_parts` 里已经带了
`AS 别名`，直接复用就出错。现在把"选择列表"和"分组表达式"分开构造。

### 坑二：JOIN 子句缺表别名

```
LEFT JOIN dim_customer ON f.customer_id = c.customer_id   -- ✗ no such column: c.region
LEFT JOIN dim_customer c ON f.customer_id = c.customer_id -- ✓
```

现在 `JoinSpec.table` 直接声明为 `"dim_customer c"`（含别名），
避免表名与条件字符串里的别名不一致——这类不一致编译器无法自行发现。

### 坑三：`SELECT "渠道" AS "渠道"` 在 SQLite 里返回字符串字面量

这是最隐蔽的一个。当双引号标识符**解析失败**时，SQLite 会回退为字符串字面量：

```sql
SELECT "渠道" AS "渠道" FROM ...   -- 每一行都返回字符串 '渠道'
```

表现是"行数正确、值全错"，很容易被误判成数据问题。
修复：内层 SELECT 必须写**真实表达式**再起别名。

### 坑四：窗口指标必须两层编译，且外层不能按别名排序

`RANK() OVER (ORDER BY SUM(x) DESC)` 里的 SUM 是聚合，不能与 GROUP BY 的
其他聚合平铺在同一层。因此：内层 CTE 先算聚合，外层再算窗口。

两个连带问题：
1. 外层若把被引用的指标再展开一遍，会变成**对聚合结果再聚合**。
   解法：展开时传入 `alias_map`，把被引用指标替换成 `agg."列名"`。
2. 外层 ORDER BY **不能引用同一 SELECT 里的别名**（SQLite 可以，标准 SQL 与
   部分引擎不行）。解法：直接重复窗口表达式。
3. 输出列顺序被打乱过（F2 变成"渠道/占比/实收金额"）。
   解法：按 `plan.measures` 原始顺序输出，不按窗口/聚合分组排列。

### 坑五（设计层）：小数位数属于口径

`客单价` 算出来是 `18028.2975`，而业务口径是 `18028.30`。
小数位数不该由各查询自行决定——它是口径的一部分。
现在 `MetricDefinition.decimals` 显式声明（金额 2 位、比率 4 位），
由编译器统一施加。另加 `ratio` 标记便于展示层格式化。

### 层检查器随之收紧

S3 引入 `re.compile` 预编译正则与常量表后，检查器把它们误报为"全局可变状态"。
修正为：**常量字面量与不可变工厂（`re.compile` / `TypeVar` / `frozenset` 等）放行**，
只拦真正的运行时状态（连接、缓存、池、单例）。
反向验证过：`CONN = object()`、`POOL = ThreadPool()` 仍会被拦下。

> 检查器过严会逼出坏代码（为过检查而把常量塞进函数），
> 过松则形同虚设。判断标准是**架构约束的本意**：拦运行时状态，不拦声明。

## 18. S4 实施记录：可插拔规划器与语义层覆盖率基线

### 模型资源：本机没有可用 LLM

开工前探测结果：`langgraph` / `openai` / `langchain` / `httpx` 已装，
但**没有任何 API Key**，Ollama 装了却零模型且服务未运行。

因此 S4 的选择是：**先把模型无关层做完，把"没有模型"当成一等状态**。
这不是退让——它正好对应本项目"用户自定义智能体组件"的设计目标。

### 两个规划器，同一契约

| 规划器 | 依赖 | 度量的是 |
|---|---|---|
| `RulePlanner` | 无 | **语义层覆盖率**（与模型能力解耦的基准线） |
| `LLMPlanner` | OpenAI 兼容端点 | **模型能力** |

两者产出同一 `LogicalPlan`，下游编译/守门/执行/缓存完全复用。
有了这条基准线，"模型带来多少增益"才可量化，而不是感觉。

`https://api.deepseek.com/v1` + `deepseek-chat`。

`describe()` 不回显密钥（已测）。

### 基线数据（黄金集 30 题，规则规划器，now=2024-06-30）

```
解析成功 25/30（83.3%）　结果正确 17/30（56.7%）
```

**5 题未解析**——全部是语义层**有意不内建**的复杂形态，规划器选择明确报错
而不是猜一个错的计划：

| 题 | 形态 | 原因 |
|---|---|---|
| A3 | 阈值 + 最值混合 | 聚合后过滤（HAVING） |
| B5 | 分组后按聚合值过滤 | HAVING |
| C4 | 本月 vs 上月 | 条件聚合转列 |
| C6 | 按天 + HAVING | HAVING |
| F1 | 与平均值比较 | 标量子查询 |

**8 题解析但结果不符**——多为窗口/CTE 类（E2 分组内 TopN、E3 累计、E4 分区排名）
与按周分桶（C3）。这些正是 `raw_select` 逃生通道的适用场景，
在有模型时由模型生成，或后续以 few-shot 形式进知识库。

> 关键判断：**语义层不该为了覆盖率把自己撑成 SQL 生成器**。
> 56.7% 这个数字本身就是有价值的信息——它说明语义层覆盖了"取数"类问题，
> 而"分析"类问题需要模型或示例支持。这正是后续 S6 知识库要补的部分。

### 规划器实现中踩出的坑（都是静默错误）

规则规划器的第一版只有 **23%**，全部问题都是**能跑但结果错**：

| 坑 | 表现 | 修法 |
|---|---|---|
| **把 `description` 当匹配关键词** | "客户等级"的描述含"客户"→"客户数"问题多出一个客户姓名分组列 | 只用 名称/label/synonyms 建键表，**绝不用描述** |
| 指标未占位，维度抢词 | "客户数"的"客户"又被 `customer_name` 命中 | 指标先匹配并记录**文本区间**，维度匹配跳过已占用区间 |
| `分别` 被当成分组信号 | "华东地区的…分别是多少"多出一个地区列 | 区分"分组类"（各/每/按/哪个）与"仅多列输出类"（分别） |
| 时间粒度词被剥离 | "2024年上半年…按月列出"丢失月份分组 | 分组判断回**原问题**取词，不用剥离后的文本 |
| 组成项与比率同时输出 | "…占…的比例"输出分子分母+比率三列 | 比率问句只输出派生比率 + 被点名的基础指标 |
| 分母解释被当成点名 | "占该地区全部订单数的比例"里的"全部订单数"被判为要输出的列 | 被派生指标引用且出现在分母解释里的组成项，不算点名 |
| 窗口指标内层缺依赖 | `revenue_rank` 引用 `net_revenue`，内层未先算出 → `no such column` | 编译时把窗口指标的**依赖指标**也纳入内层 CTE |
| 过滤与指标内置条件打架 | `paid_order_count` 固定筛"已支付"，与 `IN (已退款,已取消)` 叠加得 0 | 注册**条件聚合扩展指标**（`SemanticModel.extend_metrics`） |

`SemanticModel.extend_metrics` 是顺带得到的架构收获：它既是规划器兜底的手段，
也正好是后续「用户自定义指标」的入口——自定义指标最终也要进语义模型，
才能被编译、被校验、被缓存指纹覆盖。

### 编排层的一个设计取舍

**没有引入 LangGraph，用的是显式顺序管线。**

理由：P0 流程是线性的（规划 → 编译 → 查缓存 → 守门 → 执行 → 写缓存）。
LangGraph 的价值在分支/循环/多 Agent，现在引入只增加抽象成本。
`GraphSpec`/`NodeSpec`/`Edge` 的数据结构已支持任意拓扑，
需要时把它编译成 LangGraph 图即可——**这一步不会成为返工点**。

同时验证过的链路行为：
- 缓存命中（含"换说法但逻辑计划相同"仍命中）
- 缓存按数据源隔离
- 无法解析时返回 `unresolved` 且**不返回 SQL**（不编造查询）
- 空结果回显生效的过滤条件
- 查询历史落盘并记录所用规划器
- 各阶段耗时 trace（供回放排障）

### S4b：接真实模型后的实测（DeepSeek）

模型确认可用：`deepseek-chat`（实际路由到 `deepseek-flash`），
JSON 模式正常，往返 400~2500ms。经 `scripts/check_llm.py` 自检。

对黄金集 30 题的实测对比：

| 规划器 | 严格正确 | 规划成功率 | p50 延迟 | 成本 |
|---|---|---|---|---|
| `RulePlanner`（无模型） | **17/30 = 56.7%** | 25/30 (83.3%) | ~10ms | 0 |
| `LLMPlanner`（DeepSeek） | **18/30 = 60.0%** | 27/30 (90.0%) | ~1200ms | 按 token 计费 |

#### ★ 关键发现：两者强互补

```
两者都对   16 题
仅规则对    1 题  (D7 毛利率：三列派生指标，规则规划器处理更稳)
仅模型对    2 题  (B6 退款率、D4 销量 TopN)
两者都错   11 题
合并上限   19/30 = 63.3%
```

**模型只比规则高 3.3 个百分点，但代价是 120 倍延迟与真实费用。**
单看这个数字，"上模型"的性价比并不高——真正的价值在于两者覆盖了**不同的题**。

因此推荐**混合策略**（规则优先 + 模型兜底）：

```
RulePlanner 命中        → 零延迟、零成本、结果确定可复现（约 2/3 的题）
RulePlanner 报 UNRESOLVED → 交给 LLMPlanner
```

理由不只是准确率，更是**确定性**：规则规划器对同一问题永远给出同一计划，
缓存指纹稳定、结果可复现、便于回归；模型则适合处理规则表达不了的问法。
个人工具场景下，"常用问题快且免费、冷门问题才花钱"是更合理的行为。

#### 模型失败的分布（说明下一步该补什么）

| 类别 | 题号 | 性质 |
|---|---|---|
| 规划失败（3） | B5 / C6 / F1 | 语义层未覆盖的复杂形态 |
| 执行失败（2） | A3（聚合放进 WHERE，应 HAVING）/ C3（排序字段"周"未定义） | 需要编译器给出更明确的错误引导 |
| 数值/列不符（7） | C4 / C5 / D3 / D7 / E2 / E3 / E4 | 窗口/CTE/累计类；多为"行数对但列缺失" |

两类共同指向**同一个缺口**：窗口、CTE、条件聚合、HAVING 这些形态
既不在语义层内建，也没有 `raw_select` 或 few-shot 示例兜底。

**这正是 S6 知识库要补的部分**：把这类查询作为 (问题, SQL) 示例入库，
让模型照着改，而不是指望它从零推导多列派生结构。

#### 顺带确认的事

- `LLMPlanner` 的产出校验有效：编造指标/维度会被拦下并降级
- Prompt 中**不含物理表名**（模型面对业务概念，不猜 JOIN 路径）——已断言
- `describe()` 不回显密钥——已断言
- Key 通过环境变量注入，**未写入任何文件、未进 git**

> 安全提醒：会话中明文传输过的 Key 应视为已泄露，用完请到控制台轮换。

### S4c：混合策略（规则优先 + 模型兜底）

`HybridPlanner`：规则规划器命中就用规则，只有它抛 `SemanticResolutionError`
时才调用模型。默认模式为 `auto`（有可用模型 → hybrid，否则退化为 rule）。

实测（黄金集 30 题，同一 Key、同一 now）：

| 模式 | 严格正确 | 模型调用次数 | 说明 |
|---|---|---|---|
| `rule` | 17/30 = 56.7% | 0 | 零延迟零成本 |
| `llm` | 18/30 = 60.0% | 30 | ~1200ms/次 |
| `hybrid` | 17/30 = 56.7% | **2** | 规则处理 25 题，模型兜底 2 题 |

#### 诚实的结论：这是**成本/速度优化**，不是准确率提升

写这一节是为了避免日后误解这个模块的定位：

- **收益**：模型调用从 30 次降到 2 次（**省 93%**），
  且 25 道题走的是确定性路径——同一问题永远产出同一计划，
  缓存指纹稳定、结果可复现、便于回归。这在个人工具场景里是实打实的价值。
- **代价**：准确率与 rule-only 持平（17），**低于 llm-only（18）**。

#### 为什么没能接近合并上限 19

原本期望 hybrid 拿到"规则独对 + 模型独对"的并集，实际只拿到 17。
根因是**规则规划器会"错误地自信"**：

```
它对 B6（退款率）、D4（销量 TopN）给出了看似正常但答非所问的结果，
状态是 ok，不抛 UNRESOLVED，因此永远不会触发模型兜底。
```

兜底只覆盖了**错误路径**（解析失败），没覆盖**错误的正向结果**。

#### 试过但无效的补救：列依据检查（`RulePlanner(strict=True)`）

思路：校验每一列在问题里是否有"明文依据"（派生指标须被点名、
分组维度须有分组信号词），没有就拒绝、让位给模型。

实测结果：**只拒绝 3 题（A4 / A5 / F2），而这 3 题规则规划器本来就答对**，
对准确率毫无帮助，反而多花 3 次模型调用。诊断脚本：
`scripts/diag_rule_confidence.py`。

因此 `strict` 保留为**安全护栏**（防止"看似正常但答非所问"的输出被当作
确定答案返回），并在文档与代码注释里明确标注**它不是准确率手段**。
把它说成提升会变成自欺。

#### 下一步的正解：验证式混合（recorded，未实现）

真正能接近上限的是**验证**而非**兜底**：

```
规则产出计划 → 模型只做一次"这个计划是否回答了该问题"的验证
             → 通过则用（零额外规划成本）
             → 不通过则让模型重新规划
```

代价是每题多一次模型调用（无法像现在这样 93% 免费），
收益是能抓住"错误的正向结果"。这属于 S6 知识库之后的优化项。
当前先用 hybrid 的成本优势，把它记录在此以免遗忘其缺口。

## 19. S6 实施记录：知识库与验证式混合（两个负结果）

S6 的目标是"知识入库提升准确率"与"验证式混合抓住规则答错"。
**两个目标都没达成**，但过程中的发现比结果更有价值。

### 已交付的能力（机制层面全部可用）

| 能力 | 状态 | 说明 |
|---|---|---|
| 条目管理 | ✅ | 免审 + 版本留痕 + 回滚（回滚生成新版本号，不复用旧号） |
| 停用开关 | ✅ | 停用后立即退出检索与 few-shot |
| 混合检索 | ✅ | BM25 + 向量 + **RRF 融合**（只用名次，无需跨路归一化调参） |
| 测试检索 | ✅ | 返回命中条目与 `why`（如 `bm25#1`），让"知识是否生效"可验证 |
| 库注释自动生成 | ✅ | 首次连接从元数据生成 schema 条目；**幂等**，不覆盖用户编辑 |
| few-shot 注入 | ✅ | 只召回 `sql_pair` 且 `enabled` 的条目，停用的不污染 Prompt |

一个实现细节值得记：`PRAGMA table_xinfo`（S2 的修正）在这里再次见效——
自动生成的 `fact_order` 条目**包含生成列 `amount`**，
否则模型会以为这一列不存在。

### 负结果一：few-shot 贡献 0

**评测设计（防自欺）**：把 A/B/C 三类 17 题入库，只测 D/E/F 三类 13 题。
若把 30 题全入库再测这 30 题，只是答案泄露，测的是检索准不准。

```
llm-only 无知识库     7/13 = 53.8%
llm-only 有 few-shot  7/13 = 53.8%
知识库贡献: +0 题（既无答对，也无答错）
```

**原因（判断）**：入库的 A/B/C 是"基础过滤/分组聚合/时间趋势"，
留出的 D/E/F 是"多表关联/窗口排名/子查询"——**结构形态不同**，
few-shot 提供不了可迁移的模式。

**这指向的真正瓶颈**：失败集中在**语义层表达能力**，而不是 Prompt 示例。
留出集里 D3（少客户数列）、E2（分组内 TopN）、E3（累计）都不是"照猫画虎"能解决的，
而是**语义模型里根本没有对应的指标**——
比如 E2 需要 `名次 = ROW_NUMBER() OVER (PARTITION BY category ...)`，
而模型只有全局 `revenue_rank`（`PARTITION BY` 都没用），
规划器再聪明也拼不出来。

### 负结果二：验证式混合不划算

新增 `VerifiedHybridPlanner`：规则产出计划 → 模型验证是否切题 →
不通过则模型重做。针对的正是 S4c 暴露的"规则会错误地自信"。

实测（全 30 题，强化判据后的验证 Prompt）：

```
hybrid_verified  18/30 = 60.0%
  规则计划被验证器拦下 8 题（rejected 8 / checked 25）
  模型调用合计：验证 25 次 + 规划 10 次 = 35 次
对比 llm-only：18/30，30 次调用
```

**验证器确实在工作**（拦下 8 题），但准确率与 `llm-only` 持平、
调用次数更多（35 vs 30）。也就是说：**验证的开销没有换来更好的结果**——
被拦下的 8 题里，模型重做后能对的那部分，
本来就直接让模型规划也能对。

### 三种模式实测汇总（同一 Key、同一 now、全 30 题）

| 模式 | 严格正确 | 模型调用 | 定位 |
|---|---|---|---|
| `rule` | 17/30 = 56.7% | 0 | 零成本零延迟，确定性 |
| `llm` | 18/30 = 60.0% | 30 | 当时实测最优 |
| `hybrid` | 17/30 = 56.7% | **2** | 省 93% 调用，准确率≈rule |
| `hybrid_verified` | 18/30 = 60.0% | 35 | 不划算（更贵，不比 llm 准） |

当时默认改为 `llm`（有模型时）。依据：当"更省"与"更准"不可兼得时，
默认取更准的那个，把省调用作为可选项留给用户按场景选择。
`auto` 在无模型时仍自动退化为 `rule`。

> **⚠ 这张表已被 S3c 推翻，保留在此作为"当时为什么这么选"的记录。**
> 语义层扩容（`docs/07`）之后重测：
>
> | 模式 | 严格正确 | 模型调用 |
> |---|---|---|
> | `rule` | 25/30 = 83.3% | 0 |
> | `hybrid` | 25/30 = 83.3% | ~1 |
> | `hybrid_verified` | 25/30 = 83.3% | ~30 |
> | `llm` | 23/30 = 76.7% | 30 |
>
> **规则规划器反超模型，`auto` 的默认已改为 `hybrid`。**
> 关键教训：`llm 18/30 vs rule 17/30` 这个差距当时看起来是"模型更强"，
> 实际上是**语义层只会表达 21/30 种问法**——规则规划器被覆盖率卡住，
> 而模型可以现场编 SQL 绕过语义层。表达能力的缺口一补上，
> 确定性规划器立刻就赢了。**读"模型 vs 规则"的准确率差距时，
> 要先问这个差距是模型的能力，还是语义层的短板。**

### 结论与下一步

S6 证明了**知识库机制本身是完备的**，但也证明了
**在当前语义层覆盖度下，"加示例"与"加验证"都不是提升准确率的有效杠杆**。

下一步的正解是**扩充语义层表达能力**，而不是继续在规划器上做文章：

| 缺口 | 需要新增的语义能力 | 影响题号 | S3c 状态 |
|---|---|---|---|
| 分组内 TopN | 带 `PARTITION BY` 的排名指标 | E2 | ✅ 已做 |
| 累计/滚动 | 累计求和指标（`SUM() OVER (ORDER BY ...)`） | E3 | ✅ 已做 |
| 分区排名 | 带分区的排名指标 | E4 | ✅ 已做 |
| 条件聚合转列 | 跨期对比维度（"本月/上月"作为列） | C4 | ✅ 已做 |
| 聚合后过滤 | HAVING 语义的指标级过滤 | A3 / B5 / C6 | ✅ 已做（A3 还差一个同义词） |
| 标量子查询比较 | "高于平均值"类比较指标 | F1 | ⬜ 见 `docs/07` 第 6 节 |

这 11 题占了当时失败的大部分。它们都是**可复用的业务口径**，
做进语义层后所有问法都受益——这才是"让准确率上去"的着力点。

**结果（S3c 实测）**：真实语义计划 21/30 → 28/30，
规则规划器 17/30 → **25/30 = 83.3%**，且没有一道题靠调 Prompt 或加示例。
详见 `docs/07-语义层表达能力.md`。

> 记这条负结果的意义：避免下次又去调 Prompt 或加示例。
> 数据已经把瓶颈指出来了——**在语义层，不在规划器**。
> 后来照着做了，也确实涨了 8 题。
