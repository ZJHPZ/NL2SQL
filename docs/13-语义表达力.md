# 13 · 语义表达力：时间粒度与标量比较（M3）

> 这一章记录 M3：不是"让规划器更聪明"，而是**给语义层补两个它根本说不出来的词**。
>
> 结论先放这里：黄金集 **25/30 → 29/30（96.7%）**，剩下的 D3 是黄金集题面
> 与 SQL 口径不一致，不是能力缺口；同时把 M1 留下的 C3 跨引擎缺口**正确**
> 闭合（C 节逐题等价 29/30 → **30/30**）。
>
> 最值钱的两个发现：
> 1. **"每周"解析出了 `grain=week` 却没人消费**——表达力缺口不在推理，在契约
>    （§1、§2）。
> 2. **一个只在"先问过别的题"时才出现的 bug**：规划器会改共享语义模型，B6 在
>    问过某些题之后从 2 列变 4 列（§4）。单题测试永远是绿的，序列测试才抓得住。
>
> 另外如实记录一条没做完的：`pivot + having/qualify` 的组合限制**没有**在
> M3 解开（§7），理由和代价都写在文档里，而不是留一个"看起来支持"的空壳。

## 1. 先看失败长什么样：25/30 里没有一题是"模型不够聪明"

M3 开始前，规则规划器在黄金集上是 **25/30 = 83.3%**，失败五题：

| 题 | 问题 | 失败表现 | 根因 |
|---|---|---|---|
| A3 | 单个订单成交金额超过 5000 元的订单有几笔？最高一笔多少？ | 只返回"最高成交金额"一列 | 指标词表里"几笔"没有对应指标 |
| B6 | 各地区的退款率 | 返回 3 + 1 列（分子分母没被剪掉） | 解释性成分判定依赖一个脆弱的 30 字符窗口 |
| C3 | 每周的有效订单数 | 返回不分组的一行 661 | `grain=week` 已解析，但 `dims=[]`——没有"周"这个维度可加 |
| D3 | 新客户和老客户各贡献了多少实收金额？ | 少"客户数"一列 | 黄金题面与黄金 SQL 口径不一致（见 §5.3） |
| F1 | 消费金额高于全部客户平均消费金额的客户 | 直接 `UNRESOLVED` | 语义层没有"消费金额"这个词，也没有"与另一个聚合比较"的表达 |

五题里，A3/B6/F1 的词表问题、C3 的维度问题、F1 的算子问题，**没有一题是
"规划器规则写少了"**。C3 尤其典型：时间解析器已经把 `TimeRange.grain` 填成
`week`、`explicit_grain=True`，但计划构造时没有任何代码消费它——因为
`SemanticModel` 里没有一个叫"周"的维度，而在 `substr(...)` 里写死
`strftime` 又会把语义文件绑死在一个引擎上。

这就是 M3 的选题：**瓶颈是语义层的表达力，不是规划器的强度。**

## 2. 原语一：时间粒度（声明与方言展开分离）

### 2.1 契约：维度只声明"我是哪个桶"

`DimensionDefinition` 增加一个字段：

```python
grain: str | None = None   # day / week / month / quarter / year
```

语义约定：`grain` 非空时，`expr` 被解释为**时间字段**（不是表达式），
截断写法由编译器按数据源方言生成。

```yaml
# golden_set/metrics.yml（dbt 没有"维度按粒度截断"的对等物，属于结构扩展）
- name: week
  type: categorical
  expr: order_date            # 只写时间字段
  description: 年周
  meta:
    nl2sql:
      grain: week
      synonyms: [周, 年周]
```

**为什么不在语义文件里写 `strftime('%Y-%W', order_date)`**：M1 已经证明这会
出事——同一个计划拿到 MySQL 上直接 `FUNCTION ... strftime does not exist`，
而"换个写法"又可能写错（`%W` 与 `%v` 语义不同，见 `docs/11` §5）。
语义文件一旦含方言，换引擎就要改文件，而改错**不会报错**。

### 2.2 编译器：所有出口必须走同一个函数

`SqlCompiler._dimension_expr_sql(dim)` 是唯一出口：

```
没有 grain        → dim.resolved_expr()（普通维度原样用）
grain + select    → CompileError（粒度要插方言函数，select 是整段 SQL，插不进去）
未知方言          → CompileError（列出已支持方言）
未知粒度          → CompileError（列出该方言支持的粒度）
否则              → 模板.format(x=dim.resolved_expr())
```

映射表 `_DIALECT_TIME_GRAINS`：

| 粒度 | sqlite | mysql |
|---|---|---|
| day | `strftime('%Y-%m-%d', x)` | `DATE_FORMAT(x, '%Y-%m-%d')` |
| week | `strftime('%Y-%W', x)` | `DATE_FORMAT(x, '%Y-%u')` |
| month | `strftime('%Y-%m', x)` | `DATE_FORMAT(x, '%Y-%m')` |
| quarter | `strftime('%Y', x) \|\| '-Q' \|\| ((CAST(strftime('%m', x) AS INTEGER) + 2) / 3)` | `CONCAT(YEAR(x), '-Q', QUARTER(x))` |
| year | `strftime('%Y', x)` | `DATE_FORMAT(x, '%Y')` |

MySQL 的 `%u` 是"周一为一周之始、00–53"，与 SQLite 的 `%W` 对齐；
**没有用 `%x-%v`**（ISO 周），因为 M1 已经指出那是语义不同、看起来像的错答案。

### 2.3 关键约束：SELECT / GROUP BY / ORDER BY / HAVING / WHERE 一个出口

漏掉任何一处都会产生"按周分组、按原始日期排序"这类错位，而且两处用的是
同一个维度名，**SQL 看起来完全正常**。所以 M3 把六个调用点统一换成
`_dimension_expr_sql`：

* `_dimension_sql`（SELECT）
* `compile()` 的 `dim_group_exprs`（GROUP BY）
* `_compile_two_level` / `_compile_three_level` / `_compile_pivot` 的 GROUP BY
* `_order_sql` 的维度分支（ORDER BY）
* `_having_sql` 的维度分支（HAVING）
* `_filter_sql` 的维度分支（WHERE）

测试里用 C3 的 SQL 直接断言 `strftime('%Y-%W'` **出现 3 次**
（SELECT / GROUP BY / ORDER BY）——数量断言比"包含"更能守住这个约束。

### 2.4 顺带收编 month/day，并闭合 M1 的缺口

M3 之前 month/day 是 `substr(order_date, 1, 7 / 1, 10)` 写死的。迁移到
`grain` 后 SQL 逐字等价（`strftime('%Y-%m')` 与 `substr(...,1,7)` 输出一致），
但语义文件不再含方言。`tests/test_s3b_dbt_loader.py` 要求 dbt 模型与手写
参考模型 30 题逐题一致，两处同步改，测试仍然全绿。

**M1 的 C3 缺口因此闭合**：黄金计划 `golden_plans.py` 的 C3 从 `raw_select`
改成结构化计划（`dimensions=("week",)` + `time_range=half_year("week")`），
`tests/test_m1_mysql.py` C 节从 29 equal + 1 known_gap 变成
**30/30 逐题一致**；D 节两端仍是 29/30、失败题只有 D3。

## 3. 原语二：标量比较（与"另一个聚合结果"比）

### 3.1 为什么它不能塞进 HAVING 或 qualify

三种"聚合之后过滤"看起来都像，实际比的东西不同：

| 构造 | 左边 | 右边 | 例子 |
|---|---|---|---|
| HAVING | 聚合值 | **常量** | 品类实收金额 > 20000 |
| qualify（三层） | 窗口值 | 常量 | 每个品类内部排名 ≤ 2 |
| **compare（新增）** | 聚合值 | **另一个聚合的结果** | 客户消费金额 > 全体客户平均消费金额 |

"高于平均"如果把右边当成常量，会得到"先按客户求和、再和某个数比"；
如果硬套 qualify，右边只能是窗口值。两种错法都**能跑出结果**，只是口径不同
——这正是它必须进契约、而不是在规划器里打补丁的原因。

### 3.2 契约：`against` 是必须显式建模的歧义

```python
@dataclass(frozen=True)
class ScalarCompare:
    measure: str            # 被比较的指标（必须已在 plan.measures 里）
    against: str = "all"    # all=整张表（只保留时间范围） / result=当前结果集
    op: str = ">"
    factor: float = 1.0     # 阈值倍数：> 1.2 × 平均
```

`against` 的两种含义给的是**两个不同答案**：

* `all`：分母是整张表（只保留时间范围，忽略其它行过滤）
* `result`：分母是当前结果集（本计划 WHERE 之后、HAVING 之前的聚合）

两者只在"还有额外行过滤"时才不同——但那时**选错是一个安静合理的错误答案**。
所以把它做成契约参数，而不是让实现悄悄选一个。文档里用一句话提醒：
"用户说'全部客户平均'是 all；说'组内/各自平均'是 result；中文单说'高于平均'
默认 all。"

### 3.3 编译形状：聚合 CTE + 标量子查询

```
WITH agg AS (                      -- 当前结果集（全部过滤 + 时间范围）
    SELECT 维度..., 指标 AS "指标名"
    FROM ... WHERE ... GROUP BY 维度
)
[, base AS (...只保留时间范围...)]  -- 仅 against=all 且还有其它过滤时
SELECT ... FROM agg
WHERE agg."指标名" > (SELECT AVG("指标名") FROM agg|base)
```

**为什么用子查询而不是 `AVG(...) OVER ()`**：窗口函数不能出现在 WHERE 里，
用它就得再套一层（等于三层编译）；而这里"平均"只是一个标量，子查询直接、
也不会把窗口的分区/排序语义混进来。

`factor` 直接乘在子查询后面（`> (SELECT AVG(x) FROM agg) * 1.2`）。
不成立的组合在编译期报错：与 pivot 组合、与 qualify 组合、指标不在计划里、
指标是窗口指标（窗口值没有"整表平均"的概念）——报错文案都说明原因。

### 3.4 规划器怎么识别（规则版）

`_match_scalar_compare(question, metrics)`：

* 正则要求**同一小句**里出现 `<比较词>…平均/均值`，没有"平均"就返回 None
  ——"实收金额高于 5000"是 HAVING/行过滤，混淆会得到口径完全不同的答案；
* 被比较指标取**比较词之前最近出现**的那个（F1 里"消费金额"出现两次，
  第一次才是被比较对象，第二次只是复述平均值的口径）；
* 退化路径：指标词只出现在"平均"那侧（"高于平均消费金额"）时，回退到
  "问句里最早出现的非窗口指标"——**宁可猜一个，也不让识别失败安静退化成
  "没有比较"**（那是这类需求最典型的隐蔽错误）；
* `against`：问句含 组内/本组/各组/各自/同类 → `result`，否则 `all`；
* `factor`：识别 `(\d+(?:\.\d+)?)倍`。

计划 notes 里会写一行"★ 标量比较：… （不是 HAVING——比的是聚合值，不是常量）"，
让结果页能解释口径，也方便排查"为什么这题没按我想的筛"。

## 4. 一个被"共享可变语义模型"放大的坑（本轮最有意思的 bug）

修 B6 时发现：**同一道 B6，单独问返回 2 列（正确），在问过别的题之后问返回
4 列（错误）**。它不是 M3 引入的，而是 M3 的 A3 修法（给指标加词）让触发
顺序更容易发生——值得完整记录。

### 4.1 现象与根因

B6 的期望是"地区 + 退款率"2 列。规划器先匹配到三个指标
（退款率、退款订单数、全部订单数），再由 `_prune_component_metrics` 剪掉
比率的分子分母——前提是 `_is_explanatory(label, question, model)` 认为
"分母只是口径解释，不是用户要的列"。

旧实现的判据是：

```python
idx = question.find(label)          # "退款率" 只在句尾出现
before = question[idx - 30:idx]     # 只看它前面 30 个字符
```

B6 题面里"占该地区全部订单数的比例"离"退款率"超过 30 字符，于是直接判 False
→ 三个指标全留下 → 4 列。

更麻烦的是**顺序依赖**：`_refine_metrics_by_status`（把"已退款和已取消各有多少
笔"变成条件聚合指标）会调用 `self._model.extend_metrics(...)`，往**共享**
`SemanticModel.metrics` 里注册一个 label 为"订单数"的扩展指标。之后任何
`_is_explanatory` 的调用都会在"全部订单数"里子串命中这个短 label"订单数"，
于是 B6 的判定被污染。单跑 B6 时那个扩展指标还不存在，测试永远绿。

### 4.2 修法

`_is_explanatory` 重写成两个机制：

1. **全句找比率短语**：`占[^，。；？]*?(?:的)?(?:比例|占比|比重|率)`，
   不再用固定字符窗口；
2. **长 label 先消费**：按 label 长度降序遍历指标，本题里"全部订单数"先被
   消费掉，就不会再被短 label"订单数"子串命中；属于比率自身组成项
   （`metric_refs(ratio.expr)`）的词直接吞掉，不属于的才判为"列举型"。

### 4.3 教训（写进测试）

* 规划器**会改变共享语义模型**是设计现状（扩展指标要跨题复用），
  所以任何依赖词表的判定都必须对"词表被前一道题改过"保持稳定；
* 这类 bug 只能用**序列**测试抓：`tests/test_m3_semantics.py` 的 [E] 段先问
  "已退款和已取消各有多少笔"，再问 B6，断言列数仍是 2。单题测试再全也抓不到；
* 修完不是"改一行"，而是把判据从"位置启发式"换成了"结构 + 消费顺序"——
  前者在词表变化时必然反复。

### 5.2 跨引擎（顺带闭合 M1）

`tests/test_m1_mysql.py`：

```
[C] 30 题逐题等价（逻辑计划 → 各地方言编译 → 执行 → 比结果集）:
    30/30 equal   （M1 时是 29 + 1 known_gap）
[D] 端到端: SQLite 29/30 = MySQL 29/30，失败题（两边相同）: ['D3']
```

注意 C 与 D 的差别：C 比的是"同一份逻辑计划在两个引擎上结果是否一致"
（30/30），D 比的是"整条系统在两边准确率是否一致"（29/30，且失败题集合
相同）。C3 在两个引擎上都返回 26 个周桶。

### 5.3 D3：不修，而是记录（黄金集口径不一致）

D3 题面："2024年上半年，新客户和老客户各贡献了多少实收金额？"
黄金 SQL 却多返回一列 `COUNT(DISTINCT c.customer_id) AS 客户数`。

题面没问客户数。**不写规划器硬编码**（比如"看到新客户就补客户数"）——
那会把黄金集的一个瑕疵固化成能力。如实记在这里和 `docs/10` 的 M3 说明里，
29/30 已是 M3 验收线（≥28/30）之上。

### 5.4 其它

* dbt 语义文件可移植性：**70.6%**（`meta.nl2sql.*` 结构扩展占 29.4%；
  `grain` 是其中最新的一项，它没有 dbt 对等物——dbt 的时间粒度挂在指标的
  `time_grains` 上，而不是维度上）；
* `tests/test_m3_semantics.py` 约 **6.5s**（含黄金集 30 题 + 两个引擎的编译，
  不需要 Key、不需要 MySQL）；
* 全量离线回归：**15/15 通过**；3 个需 Key 套件未跑（未跑 ≠ 通过）。

## 7. 这一轮没做的事（如实记录）

1. **`pivot + having` / `pivot + qualify` 仍然报"暂不支持"。**
   `docs/10` 的 M3 计划里写了"不再报暂不支持，有测试覆盖"。实际没有做：
   pivot 之后的结果是"桶宽表"，HAVING 要过滤的是**内层聚合值**还是
   **外层桶列**，字段语义和新 SQL 形状都需要先定义清楚。为了通过验收线
   而写一个"看起来支持"的假机制，比不做更糟——所以保留报错（报错文案
   明确说"暂不支持组合使用"），把这一条移到 M4 之后再评估。

2. **`quarter`/`year` 粒度只有映射，没有题验证。**
   映射表与 `_GRAIN_WORDS` 都有它们，但黄金集里没有对应问法；规则规划器
   的 quarter/year 识别路径未经端到端验证（只在 M3 单元层面确认"未知粒度
   会报错"）。留出集里也没有（不想在 M3 快结束时造题造出个"看似验证"）。

3. **真实 dbt 项目的 `date_trunc` 未验证。**
   黄金库 `order_date` 是 TEXT，`strftime`/`DATE_FORMAT` 直接可用；真实
   数仓里列是 DATE，截断表达式应换成 `date_trunc('week', x)`。`grain`
   抽象支持这一点（模板可替换），但没有在真 dbt 项目上跑过，属于边界声明。

4. **留出集建立了，但开发期没跑。**
   20 题 / 6 类 / 118 行答案，由**手写 SQL 执行**生成
   （`golden_set/heldout.json`，`scripts/make_heldout.py` 可复现，
   `--check` 校验）。按计划它只在 M4 实验里跑一次，用来回答"语义层改动
   是不是只对黄金集过拟合"。

## 8. 可复用教训

1. **表达力缺口和推理缺口要分开修。** C3 的 `TimeRange.grain` 一直是对的，
   缺的是"周"这个维度；F1 缺的是一个算子加两个词。如果先去加规划器规则，
   会在错误的层上修，而且每加一条都是特例。
2. **"声明与方言分离"是便宜的可移植性。** 语义文件只写"按周"，截断由
   编译期按 `SourceCapabilities.dialect` 展开——同一份文件在两个引擎上
   给出同一列、同一组合，测试也只需要断言"计划一致 + 结果一致"。
3. **相似的东西要显式区分，不能靠实现猜。** HAVING（比常量）、qualify
   （比窗口值）、compare（比另一个聚合的结果）三者左边都像"聚合后的值"，
   但右边完全不同；`against` 的 all/result 也一样。**歧义不是实现细节，
   是契约的一部分。**
4. **共享可变模型的测试要跑序列。** 词表被前一道题改过、计划缓存键漏字段、
   扩展指标累积——这些在单题测试里都不会暴露。
5. **报错文案是能力的一部分。** "未知方言""未知粒度""grain 和 select 冲突"
   的报错都列出了可用值或说明了原因；M3 的测试直接用报错文案做断言，
   改坏了会红。
