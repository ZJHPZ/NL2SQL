# 04 插件与工具管理

> 回答三个问题：**装了什么、能不能管、什么能配**。

---

## 1. 起点：三条真实痛点

插件原本靠文件系统（放目录 + 写 `plugin.toml`），开发者能加，但：

| 痛点 | 具体表现 |
|---|---|
| **看不到** | 界面看不到装了哪些插件、贡献了哪些工具、为什么某个工具没生效 |
| **管不了** | 不能启用/停用某个工具 |
| **配不了** | Prompt、模型绑定、循环参数只能改代码 |

---

## 2. 一个前置决策：配置放在文件里

| 方案 | 结论 |
|---|---|
| 数据库 | ❌ 看不到、没法版本控制、换机器要导出 |
| **配置文件** | ✅ 采用 |

理由：目标用户是个人开发者，配置文件他**能看懂、能直接改、能进 git**。
数据库存配置在个人场景是过度设计。

配置文件是 `config/nl2sql.toml`，**不存在时一切按代码默认运行**——
不会因为"忘了建文件"就起不来。

---

## 3. 能力可否在界面修改：一个需要讲清的取舍

原始设计里，能力（Capability）在装配时授予，未授予的工具**根本不注册**
（它的说明也就不进入模型的工具清单）。

我最初的立场是"界面不能改能力"。**但这条被推翻了**，理由是：

> 面向个人工作者的工具，**用户就是自己数据的主人**。
> 替他做决定是越权。

### 推翻之后补上的三件事

自由度和知情权要配套，否则就是把风险藏起来：

**① 每项能力标注 `risk` 与 `unlocks`**

```json
{"name": "source.write", "risk": "high",
 "unlocks": "执行 INSERT/UPDATE/DELETE/DDL（当前无工具实现）"}
```

风险元数据**放在后端**（`_CAPABILITY_META`），不在前端硬编码——
新增能力时只改一处，界面自动跟上。

**② 界面摆出"还有几道防线"**

```
还有几道防线
  只读守门（guard.read_only）    开启
  存在实现写操作的工具            否
  强制行数上限                   1000

说明：授予 source.write 不会立即解锁写操作：当前没有实现写操作的工具，
      且 guard 的只读守门独立于此。真正的写操作防线在 guard（read_only）。
```

这条最关键。用户点下"授予"时应该知道**自己实际改动了什么**——
而不是以为点了一下就能删库。

**③ 授予高危能力时返回提示，收回能力时提示受影响工具**

收回 `clarify.ask` 会让 `clarify.ask` 工具不再注册。这是用户可能
没预料到的后果，必须明说而不是静默生效。

## 4. 三条需求的落地

### ① 看得见

`GET /api/admin/tools` 返回：

| 字段 | 用途 |
|---|---|
| `tools[]` | 工具全集（**含未注册的**），带 `origin` / `enabled` / `registered` / `risk` / `missing_capabilities` / `reason` |
| `plugins[]` | 插件清单：版本、说明、声明能力、贡献的工具、警告 |
| `plugin_errors[]` | 加载失败原因（越权声明、坏插件、白名单外） |
| `capabilities[]` | 能力清单 + `granted` / `risk` / `unlocks` |
| `safety` | guard 状态、是否存在写工具、**一句人话说明** |
| `loop` | 当前循环参数 |

**一个关键实现点：必须枚举"全集"而不是只看注册表。**

被停用或未授权的工具**不在注册表里**。若界面只列注册表，用户就看不到
它们，也就无从恢复。所以 `builtin_tool_specs()` 单独列出工具规格，
`plugin_manifests` 记下插件贡献的全部规格。

### ② 管得了

`POST /api/admin/tools/toggle` → 写入配置文件的 `[tools].disabled`。

* **落盘**：重启后仍保持
* **停用主力工具时给退化警告**（`nl2sql.solve` / `clarify.ask` / `schema.describe`）
* 停用不存在的工具返回 400

方向性很重要：**停用是"收紧"，与能力授予方向相反**，所以默认允许、无需额外确认。
而能力授予是"放宽"，所以要给提示。

### ③ 配得了

| 接口 | 内容 | 生效方式 |
|---|---|---|
| `POST /api/admin/loop` | `max_steps` / `max_repeat` / `temperature` | **热生效** |
| `POST /api/admin/capabilities` | 授予 / 收回能力 | 需 `reload` |
| `GET/POST /api/admin/config` | 配置文件原文 | 校验后热生效 |
| `POST /api/admin/reload` | 重新装配工具集 | — |

**热生效怎么做到的**：循环参数与 Prompt 模板都不涉及模块导入，
所以 `apply_runtime_settings()` 可以就地更新运行中的 `RunConfig`。

**配置原文保存先校验再落盘**：写临时文件校验，通过才覆盖正式文件。
非法内容直接拒绝且**原文件不受影响**——否则用户手抖一下就把能用的配置弄没了。

## 5. 两件明确不做的事

### 不做运行时热插拔插件代码

Python 卸载已导入模块有诡异问题（旧引用仍活、单例残留），
个人工具不值得冒这个险。

界面上提供「重新扫描并重装工具集」（改能力/停用清单后用），
但**新增插件目录需重启进程**——这个限制在界面上明说，不假装热插拔。

### 不做插件市场 / 依赖解析 / 版本升级

那是产品化。个人工具不需要。

---

## 6. 一个踩到的坑：配置路径必须可注入

第一版管理接口用默认路径 `config/nl2sql.toml`，结果测试直接写到了
仓库的 `config/` 下——**测试之间、以及多份部署会互相覆盖**对方的
停用清单与能力设置。

修法：加 `NL2SQL_CONFIG` 环境变量，路径由壳层注入。
这跟 `NL2SQL_DB` / `NL2SQL_STATE_DIR` 是同一条原则：
**核心不读环境变量，壳层显式注入**——所有会落盘的位置都必须可注入。

## 7. 界面结构

「插件与工具」页签分三块：

```
工具      插件清单（已启用：版本/能力/贡献的工具 + 「停用」按钮）
          可用插件清单（未启用：虚线卡片 + 「启用」按钮 + 为什么没加载）
          插件加载错误
          工具清单（开关 + 来源 + 风险 + 未注册原因）
能力      安全边界面板（还有几道防线）
          能力清单（开关 + 风险 + 解锁什么）
参数与配置 循环参数表单（保存即生效）
          配置文件原文编辑器（校验后保存）
```

**插件区为什么要分成两份清单。** 只列"已加载的插件"等于让默认配置下的
用户看到一片空白——他无从知道磁盘上有插件可以开。所以未启用的插件
也要列出来，并挂一个「启用」按钮，走 `POST /api/admin/plugins/toggle`：
写白名单 → 写回配置文件 → 重新装配工具集。启用后插件的工具**真的**
出现在模型清单里（`tests/test_p0_plugin_admin.py` [G] 组断言了
`registered=True`，不是只出现在界面上）。

未启用的原因必须准确，这是界面可信度的底线：

| 情况 | 显示 |
|---|---|
| 不在白名单里 | 「不在 plugins.enabled 白名单中，未加载」+ 可用的「启用」 |
| 在白名单里但导入失败 | 「已在加载范围内，但本次加载失败」+ 指向加载错误 + 提示重启 |
| `enabled = ["*"]` | 全部视为已启用；此时**拒绝**单独停用（见下） |

`["*"]`（全量加载）模式下单独停用某个插件会被 **400 拒绝**，而不是
"接受了但其实没关"。理由：静默失败的收紧操作比不提供这个操作更糟——
用户会以为关掉了。要单独控制就必须先改成显式白名单。

## 8. 验收

`tests/test_p0_plugin_admin.py`，覆盖：

| 组 | 关键断言 |
|---|---|
| A 配置文件层 | 文件不存在不报错；非法值逐类给明确错误；**原配置对象未被修改** |
| B 看得见 | 工具全集含未注册的；插件来源被标注；每项能力带 risk/unlocks；透出 guard 状态；**区分已启用与磁盘可用** |
| C 管得了 | 停用**落盘**、重载后保持、未注册；停用主力工具给警告 |
| D 配得了 | 授予/收回生效；收回后依赖它的工具不再注册并说明缺哪个能力；未知能力 400 |
| E 热生效 | 改 `max_steps` 后**运行时立即生效**且落盘；非法参数 400 |
| F 配置原文 | 界面手改生效；**非法内容被拒且原文件未被破坏** |
| G 插件级启停 | 启用后进白名单、进已加载清单、工具 `registered=True`、**落盘**；停用后回到 available 且工具不再注册；不存在插件 400 并给插件名；`*` 模式下拒绝单独停用 |

G 组是"插件管理"真正的闭环：默认不加载 → 界面启用 → 真的贡献工具 →
模型能调用（`scripts/plugin_dev_trial.py` 第 6 项用真实模型验证了最后一跳）。
