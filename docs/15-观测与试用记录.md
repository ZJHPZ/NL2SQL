# 15 观测与试用记录

> M5 的交付物。对应计划：`docs/10` §4.5「体验与观测」。
> 一句话立场：**统计能回答"发生了什么"，归因能回答"为什么"，但"好不好用"
> 只能由真实使用回答——而真实试用还没开始。**

---

## 0. 结论先行

1. **观测已经能跑**：`GET /api/admin/stats` 给出问答次数、九态分布、成功率/
   失败率、缓存命中率、延迟 P50/P95、工具调用失败率、最近失败列表；数据来自
   两张 append-only 表（`query_log` / `tool_log`，`SCHEMA_VERSION = 5`）。
2. **失败归因是界面功能，不是日志功能**：`QueryStatus` 九种状态每一种都有
   "为什么 + 怎么办"的可读文案；后端 `message` 说明**本次**的具体原因，前端
   归因区块给出**该类失败**的通解。追问（`need_clarification`）单独样式，
   不算失败。
3. **真实试用尚未开始**：记录 0 条真实问题。本文件给出模板、判定标准与
   对账方法，等实际使用后填表。**未跑 ≠ 通过**——M5 的试用验收项保持开放。
4. 三个口径容易改坏的地方，已写进契约测试（`tests/test_m5_observability.py`，
   87 项断言，离线可跑）：
   - `success` 含 `empty` / `truncated`（"查到了空表"是数据事实，不是系统失败）；
   - `need_clarification` 单列，**不算失败**（追问是正常交互）；
   - 延迟分位用最近秩法，偶数样本取偏小一侧（小样本插值会造出不存在的耗时）。
5. 观测是**旁路**：写统计失败、回调抛异常都不影响查询本身。这是刻意的——
   一个"看趋势"的功能不能把主功能带崩。

## 1. 为什么单独建表，不复用 `history`

存储里原本已有 `history` 表（S2 时期为"可回看"建的），但它和观测的字段语义
不同，硬复用会让两边互相绑架：

| | `history`（回放） | `query_log`（观测） |
|---|---|---|
| 回答的问题 | "这一次问答发生了什么" | "这段时间运行得怎么样" |
| 关键字段 | `sql`、`plan_fingerprint`、`error_message` | `planner`、`runtime`、`steps`、`cached` |
| 写入方 | `AgentGraph` 管线（每次 ask） | `NL2SQL.ask` 收尾 + `AgentCore` 工具回调 |
| 读取方 | 界面历史列表、回放/复用 | 统计聚合、失败列表、试用对账 |
| 附加字段的风险 | 加一列要保证回放不受影响 | 加一列要保证统计口径不变 |

结论：拆开。统计查询走自己的索引（`idx_query_log_time`、`idx_query_log_status`），
不受回放字段的存储开销影响；`docs/15` 与契约测试保护统计口径，`history`
的字段改动不再需要审视统计。

**append-only 的理由**：统计要回答"发生过什么"，一行记录被改写，上周的
失败率就变成一个能变的数字。所以 `query_log` / `tool_log` 只插入，不更新、
不删除（清理旧数据另议，不在当前范围）。

## 2. 数据模型

`nl2sql/storage/migrations.py`：`SCHEMA_VERSION = 5`，v4→v5 建两张表。

### 2.1 `query_log`（一次问答一行）

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | INTEGER PK | 自增 |
| `created_at` | TEXT | 本地时间 ISO（秒级） |
| `source_id` | TEXT | 数据源 |
| `session_id` | TEXT | 会话（agent 模式才有）|
| `question` | TEXT | 问题原文（试用对账用）|
| `planner` | TEXT | 规划器模式（rule/llm/hybrid/agent）|
| `runtime` | TEXT | 执行器（loop/langgraph，管线路径为空）|
| `status` | TEXT | `QueryStatus` 九态之一 |
| `error_code` | TEXT NULL | 机器可读的错误码 |
| `cached` | INTEGER | 0/1，是否命中缓存 |
| `elapsed_ms` | INTEGER | 端到端耗时 |
| `row_count` | INTEGER | 结果行数（0 = 无结果）|
| `steps` | INTEGER | agent 决策步数（trace 里 `decide_*` 条数）|

索引：`(created_at)`、`(status)`。

### 2.2 `tool_log`（一次工具调用一行）

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | INTEGER PK | 自增 |
| `created_at` | TEXT | 本地时间 ISO |
| `session_id` | TEXT | 会话 |
| `source_id` | TEXT | 数据源 |
| `tool` | TEXT | 工具名（`query.read` / `nl2sql.solve` / 插件工具…）|
| `ok` | INTEGER | 0/1 |
| `elapsed_ms` | INTEGER | 工具耗时 |
| `error` | TEXT NULL | 失败原因（截断 300 字符）|

索引：`(created_at)`。

> **一个重要边界**：`tool_log` 只在 **agent 模式**有数据。线性管线（`rule` /
> `llm` / `hybrid`）不经过工具循环，工具统计天然为 0。试用若只用界面默认的
> 管线模式，工具块会是空的——这不是 bug，是模式差异。

## 3. 统计口径（改口径必须同时改这里与契约测试）

### 3.1 九种状态怎么算

| 状态 | 含义 | success | failure | 界面 tone |
|---|---|---|---|---|
| `ok` | 正常返回结果 | ✅ | | ok |
| `empty` | 执行成功但无匹配数据 | ✅ | | warn |
| `truncated` | 结果被 LIMIT 截断 | ✅ | | warn |
| `need_clarification` | 智能体追问（正常交互） | | 单列 clarify | warn |
| `unresolved` | 无法映射语义模型 | | ✅ | bad |
| `invalid_sql` | SQL 校验未过 | | ✅ | bad |
| `blocked` | 安全守门拦截 | | ✅ | bad |
| `timeout` | 执行超时 | | ✅ | bad |
| `error` | 数据源/执行报错 | | ✅ | bad |

公式：

```text
success_rate = success / total
failure_rate = failure / total        failure = total - success - clarify
cached_rate  = cached / total
```

**为什么追问不算失败**：追问是系统在信息不足时主动不猜——它出现得越多，
说明问题越模糊，而不是系统越差。把追问算进失败率，会让"主动澄清"看起来
像出错，用户下次就不敢看红色指标了。单列之后，界面能区分"我问得模糊"
和"系统答不了"。

**延迟为什么要说明分位法**：`_percentile` 用最近秩法
（`rank = ceil(p*n/100)`，偶数样本取偏小一侧）。个人场景样本量小，
线性插值会报出"12 条记录里不存在的 137.5ms"这种数字，反而误导。
P50/P95 各取真实存在的一条记录的耗时。

### 3.2 契约防漂移

`KNOWN_STATUSES` 是 `sqlite_stats.py` 里的九态元组，注释写明"与
`QueryStatus` 同步"。测试断言：

```python
set(get_args(QueryStatus)) == set(KNOWN_STATUSES)
```

**为什么值得一条测试**：如果以后加了状态却忘了统计，新状态会落到
`by_status` 之外，`total` 变小而 `failure` 按减法算——失败率会**悄悄变低**，
界面上看起来一切正常。这类漂移只能靠断言防。

## 4. 接口与界面

### 4.1 `GET /api/admin/stats?days=30`

`days` 是回看窗口（默认 30，最小夹到 1 天）。返回：

```json
{
  "total": 128, "by_status": {"ok": 96, "empty": 5, "truncated": 2,
    "unresolved": 12, "invalid_sql": 3, "blocked": 0, "timeout": 1,
    "error": 3, "need_clarification": 6},
  "success": 103, "clarify": 6, "failure": 19,
  "success_rate": 0.8047, "failure_rate": 0.1484,
  "cached": 41, "cached_rate": 0.3203,
  "latency_ms": {"p50": 812, "p95": 4210, "avg": 1302},
  "tools": {"total": 37, "failures": 2, "failure_rate": 0.0541,
    "by_tool": {"query.read": {"calls": 30, "failures": 1,
      "failure_rate": 0.0333, "avg_ms": 210, "p95_ms": 690}}},
  "recent_failures": [{"created_at": "2026-10-21T15:40:12",
    "source_id": "shop", "status": "unresolved", "question": "…",
    "error_code": "UNRESOLVED", "elapsed_ms": 12,
    "planner": "rule", "runtime": "loop"}],
  "since": "2026-09-21T15:45:00", "planner_mode": "rule",
  "runtime": "loop"
}
```

SDK 侧同一份数据：`engine.stats(since="2026-09-21T00:00:00")`。
没有统计存储时（旧装配、测试桩）返回空结构而不是报错——管理页不该整页失败。

### 4.2 前端两块

**查询页状态条**（`components/StatusBar.tsx`）：三层归因

1. 状态徽章（九态各自的中文标签，`STATUS_LABEL`）；
2. 后端 `message`：本次的具体原因（例如"列 `xxx` 不存在，候选：…"）；
3. 归因区块（`STATUS_HINT`）：该类失败的**通解**——"为什么 + 怎么办"。

以 `unresolved` 为例：徽章「未能理解」→ message 说明哪一步失败 → 归因区块
说"换用已定义的指标名，或先问『这个库里有什么数据』"。追问单独用 warn 样式
并附可点选项，明确写着"这是正常交互，不是出错"。

**管理页「使用统计」标签页**（`components/PluginAdminPanel.tsx`）：
总览（总数/成功率/失败率/追问/缓存/延迟）、状态分布 chips、工具调用表、
最近失败列表；回看窗口可选 1/7/30/90 天。按需加载（切到该标签才请求）。

## 5. 试用设计（待执行）

### 5.1 目标与规模

- 目的：拿真实问题分布，验证两件事——**失败是否可见**、**归因是否可操作**。
- 规模：≥20 条真实问题；1–2 人；2 周（每周收一次，避免一次性回忆）。
- 纪律：**试用期间不改规划器/语义模型**（避免用试用的数据反过来调参，
  那会让"试用"变成第二轮开发集）。

### 5.2 记录模板

| 列 | 说明 |
|---|---|
| `#` | 编号（试用-01 …）|
| `日期` | 提问日期 |
| `提问者` | 自己 / 同事 A / 同事 B |
| `问题原文` | **逐字**，不改写（改写会掩盖规划器的真实输入）|
| `期望答案` | 提问人认为的正确答案（含口径说明）|
| `系统返回` | 状态 + SQL 摘要 + 结果首行 |
| `是否可接受` | 是 / 否 / 部分（差异是否已在建议里解释）|
| `归因分类` | 语义未覆盖 / 规划错误 / SQL 错误 / 数据问题 / 界面问题 |
| `严重度` | P0（数字错）/ P1（答非所问）/ P2（体验差）|
| `备注` | 用户当时的反应（照抄"这啥意思"之类）|

**判定标准**：可接受 = 与期望一致，或差异可解释且系统自己说清了；
不可接受 = 数字错、口径错、答非所问。**部分**也要写清差异在哪。

归因分类与 `QueryStatus` 的对应建议：语义未覆盖 ↔ `unresolved`；
SQL 错误 ↔ `invalid_sql` / `error`；界面问题 ↔ 任意状态但归因文案没帮上忙。

### 5.3 对账方法

试用期间每个 `/api/query` 自动写一行 `query_log`，所以试用结束后：

```text
记录条数（模板） ≈ query_log 行数（days=试用窗口）
```

对不上时先查 `/api/execute`（手写 SQL 不计入问答统计）和失败的请求
（400/500 不落库）。对账能发现"用户实际问题没问出口"——比如反复重试的
问题适合作为下一轮语义层的覆盖对象。

## 8. 局限（如实写）

1. **SQLite 单机**：并发写是串行的。个人场景够用，多人同时刷会很慢；
   真要做团队版，观测应换成写入吞吐更高的存储。
2. **统计不含手写 SQL**：`/api/execute` 是用户自己写的 SQL，不是问答，
   不进 `query_log`。所以"总查询数"与"问答数"不是一回事。
3. **延迟是端到端**：含规划/模型时间，不是数据库执行时间。要做性能归因，
   看 `trace` 字段而不是 `elapsed_ms`。
4. **归因文案是静态的**：优点是可预测、可测试；缺点是遇到新失败形态
   （例如换了一个数据源以后的新错误码）要人改代码，不会自动学会。
5. **试用没有对照组**：1–2 个人、各自问不同问题，分布不可比。
   结论只能写"这个工具在我们这儿怎么用、哪里卡住"，不能写"比 X 工具好用"。
6. **工具统计只覆盖 agent 模式**（见 §2 边界说明）。
